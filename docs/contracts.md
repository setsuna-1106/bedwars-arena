## 已确定的接入方式

用户选择首版采用 Python 进程内策略调用，同时保留转向独立进程的接口条件，见 [0002](decisions/0002-in-process-agent-interface.md)。该选择已接受，尚未实现。

1. 策略接收独立的玩家观测，仅返回动作数据；不能获得引擎、Runner 或完整状态的引用。嵌套可变数据也不能共享。
2. 数据契约能显式转换为 JSON 兼容值；内部可以使用有类型的数据对象，但不能依赖函数、回调或 Python 对象身份表达动作。首版不要求实际通信或每轮 JSON 编解码。
3. Runner 统一组织决策轮与引擎推进。同一轮观测来自同一世界状态；策略调用期间不推进世界，前一策略的提交不能让后一策略提前看到执行结果。
4. 接收的动作应校验并转换为引擎拥有的数据；记录需关联对局、策略、决策轮、仿真时刻、提交动作、实际执行动作与处理结果。

决策轮与仿真 tick 分别标识；W04 已采用首期默认每 tick 决策一次，Runner 可配置正整数 k 作为决策间隔并记录，期间始终逐 tick 执行，终局可提前停止。进程内模式不提供进程隔离或可靠的强制超时中止；异常/软超时/必需包缺失的 Runner 备用动作与 W08 迟到请求处理分别按 0015/0013 执行，具体 API 未实现。

## 已确认的持续学习需求

平台需支持决策模型训练，学习过程可以跨越多局对战。新对局初始化不能隐式销毁既有学习状态；清空训练状态应与重置游戏世界分别定义。

| 状态类别 | 需要分别管理的内容 |
| --- | --- |
| 对局世界 | 地图可变状态、玩家生命与背包、事件和仿真时钟等；按本局配置初始化 |
| 本局策略会话 | 当前任务、历史观测、循环模型隐藏状态等；按局创建，等待复活和复活不自动重置，与跨局学习状态分开 |
| 跨局学习状态 | 模型参数、优化器、训练计数等（按算法需要）；新对局不能自动重新初始化 |
| 采样数据 | 轨迹、经验缓冲区等；按算法要求决定收集、使用和保留方式，不预设全部永久积累 |

按 [0015](decisions/0015-world-schedule-replay-failures-and-training.md)，自然终局与外部时限同刻两个标志均为 true、自然结果优先；淘汰玩家作为无行动被动席位直到整局终局或截断。首版对战胜/负/平奖励为 +1/−1/0，单队任务成功/失败为 +1/−1，同队固定阵容共享结果；每局策略模型版本固定，训练器可跨局更新，评估冻结，世界重置不重置学习状态。持续学习不自动授权参赛策略获取完整隐藏状态。训练算法、观测几何/可见性具体参数、完整消息 Schema 和实现继续落实。

## 已确定的空间表示

用户选择方块使用网格、玩家连续移动，并采用轴对齐矩形作为玩家平面碰撞体，位置以矩形中心为参考点，见 [0003](decisions/0003-grid-terrain-continuous-players.md)。玩家位置可以在格内连续变化；所在格子由坐标派生。矩形边与网格坐标轴平行，不随朝向旋转，边界由中心和尺寸计算。建造、拆除、移动、距离判定及观测需要使用一致的坐标约定。

网格边界已采用左闭右开的单位区域：整数格 `(i,j,k)` 对应 `[i,i+1) × [j,j+1) × [k,k+1)`，参考点所在格按各轴 floor 计算，负坐标同样向下取整。占用与碰撞查询覆盖完整身体，脚底所在格不等于承载方块；半开归属与接触合法/穿透受阻分别处理。本节其余待定“边界”限于地图有效范围、越界行为与碰撞数值细节，网格归属本身不再待选。

玩家之间可互相穿过，队友与敌人均不通过身体占位阻挡或推挤，矩形可以重叠；玩家与方块的碰撞约束继续有效。玩家矩形仍可用于命中和距离判定，攻击伤害与击退不因可穿过而取消；重叠目标选择与投射物等细则另行设计。

正式空间方案已选择 B：平面连续位置加高度与竖直速度；前期允许 A：严格俯视二维实验。B 增加第三个运动自由度，二维展示不等于严格二维物理。已确定一个方块边长为 1，水平 `(x, z)` 为矩形中心，`y` 向上为正且表示脚底高度，身体竖直范围派生为 `[y, y + H]`，不另存中心高度。正式地形采用整数坐标定位的三维方块网格，底层稀疏字典/分块存储与文件格式另定；A 测试地图限制单一行走层、无上下重叠通路，先验证平面移动、碰撞与击退，B 加入竖直速度、重力、起跳、竖直碰撞与多层通行。水平轴正向/原点/地图范围与越界、数值容差、身体尺寸、碰撞求解细节、速度与朝向的具体字段，以及 A 其余实验范围和 A/B 兼容方式仍待讨论；尚无物理实现。平台 20 Hz 时间基础见 0012，不据此推定物理积分方法；玩家生命周期分支另按下节与 0010 确定，完整字段仍待设计。

首期位置/速度等连续运动量采用 IEEE 754 binary64，时间继续使用整数 tick；展示小数截断不写回世界状态，快照保证浮点往返恢复，世界状态禁止 NaN/正负无穷。首期以固定程序版本和运行环境下重放一致为验收目标；跨平台逐位一致另验，不据此宣称已有跨平台确定性。具体快照编码、碰撞容差与物理验收尚未完成。

攻击受朝向限制且采用瞬时转向已由用户确定。朝向可直接更新到目标方向，不单独消耗仿真时间，也不旋转碰撞体；不因转身增加角速度或进度字段。用户已允许侧移与后退，移动方向和朝向独立；停止移动不清空朝向，单独转向不自动旋转已有运动方向。

具体允许角度、适用攻击类型、检查时刻及同轮转向/攻击顺序、移动输入的参考方向、战术执行器的瞄准细节仍待讨论。以上选择不代表自动命中或免除其他攻击条件。

玩家与方块的碰撞已接受路径检查与贴面滑动：表面接触合法、阻挡身体穿入，检查完整碰撞体沿途范围，斜向撞墙保留沿墙位移；B 中落地/撞顶截断对应位移并清零被阻挡的竖直速度。击退也受障碍约束。先在 A 中验证平面部分，再扩展 B 竖直碰撞；具体求解器、多面接触/容差、承载及水平击退残余状态仍待定，前文待讨论的“碰撞响应”限于这些细节。物理尚未实现，详见 0003。

主动移动采用即时响应：明确改变或停止移动意图时不模拟主动加减速，主动速度可从当前动作与规则计算；位置仍随仿真推进并受速度上限、碰撞与击退约束。停止主动移动不清空击退状态；正常决策轮未更新移动通道时继续原持续动作，算法异常/软超时或必需包缺失按 0015 的备用取消处理。

击退采用速度变化、持续运动并逐渐衰减也已由用户确定。受击期间仍允许移动，反向输入可少量削弱击退，但不能因主动操控使其停止或反转，击退始终占主导。世界状态与快照需保留延续该过程所需的速度信息，不能只记录一次位置跳变。

允许削弱的幅度、侧向控制强度、恢复正常控制的条件，以及击退运动状态的正式字段、受约束的运动合成、连续受击、衰减与碰撞规则仍待设计；不默认任意速度简单相加或控制权重。

## 已确定的玩家生命周期结构

用户接受 `PlayerState.life` 使用 `AliveState`、`RespawningState`、`EliminatedState` 三种互斥分支，见 [0010](decisions/0010-player-lifecycle-branches.md)。当前生命的位置、生命值、背包、临时效果和动作归存活分支；死亡后等待复活分支的基础字段为 `died_at` 与 `respawn_at`，分别保存本次死亡和计划复活的仿真时刻；淘汰分支的基础字段为 `eliminated_at` 与 `reason`，记录永久淘汰时刻及原因类别，不再执行正常行动。

已确定的淘汰原因类别为 `final_death`，具体类型/编码与其他类别待设计。近战、坠落等死亡方式及击杀者、死亡位置归死亡事件；淘汰原因不重复表达这些细节，无有效击杀者也不改变最终死亡的分类。淘汰后外层统计/购买进度及刚结束的生命序号继续保留。

身份、队伍、本局统计与购买进度保留在外层，购买进度仍按既定死亡规则更新；`cooldowns` 也在公共外层，按下文各组规则死亡清除或保留。生命周期通过分支转换表达，等待复活或淘汰状态不持有仍可执行的旧存活状态；历史死亡位置等另按事件/回放记录。复活构造新的存活分支，动作不自动恢复。

公共外层保存 `life_index`：首次出生为 1，每次成功复活加 1，死亡/等待复活/淘汰不递增。同一局内用 `(player_id, life_index)` 标识某条生命，跨局记录另由对局标识区分。本生命动作/效果延迟事件执行前，同时检查玩家处于 `AliveState` 且序号匹配，并继续检查动作/效果实例有效性。已发射世界实体独立运行，不因来源生命结束而自动销毁；快照恢复需保留原生命序号。

剩余复活等待由 `max(0, respawn_at - 当前仿真时刻)` 派生，不维护独立倒计时；成功构造新生命才递增序号。复活调度属于生命周期事件，不套用本生命动作/效果的存活分支检查。死亡位置与击杀归属等保存在死亡事件中，装备按外层购买进度恢复；具体时间类型与调度校验待设计。

普通死亡时确定本次复活资格：死亡结算时床仍在则进入 `RespawningState`，床已毁则进入 `EliminatedState`；等待中丢床不取消本次复活或重置等待，完成复活后下一次无床死亡才淘汰。普通死亡等待分支本身表示本次复活已获准，不额外维护 `can_respawn`，也不在倒计时归零时按当前床状态撤销资格。这是参照 BW-LIFE-04 官方历史而采用的模拟规则，不代表现行 Hypixel 全部边界已经核实。

首版每张地图为每队配置一个固定出生点及初始朝向，同队成员开局与复活共用，不引入出生点随机选择。复活位置仍表示玩家矩形中心，朝向使用该出生点配置；击退速度清零，不继承上一条命的残余击退。该清零规则不改变存活期间停止主动移动不能清空击退的约束。

其他玩家占据出生位置不阻止复活，也不因此等待或另选落点，多名玩家可以共享出生位置。地图划定覆盖完整出生矩形的禁建区域，任何队伍均不得在其中放置方块，避免建造封堵，放置失败仍不扣方块物品。地图标记的出生点承载地形不可被拆除或爆炸破坏，保证合法支撑；地形保护不授予玩家伤害/击退免疫。禁建与承载地形保护均归地图约束，具体范围/边界与格式待定。

完整分支字段、序号类型/编码与调度实现、具体冷却组的死亡处理选择、禁建与承载地形保护范围/边界、等待时长及特殊流程资格仍待落实；同 tick 破床先于死亡和训练接口的被动席位/终止标志按 0013/0015。多个出生点及其选择规则属于未来扩展，尚未采用。

## 已确定的 TeamState 基础划分

用户接受 `team_id`、`bed_state`、`upgrades`、`trap_queue`、`trap_ready_at` 五个基础字段，分别表达队伍标识、床存续、团队升级及等级、待触发陷阱队列、下一次允许触发陷阱的仿真时刻，见 [0011](decisions/0011-team-state.md)。具体类型与完整机制尚未确定；共享冷却已采用但待与 Hypixel 核验。

`bed_state` 基础字段为 `status`（存在/已摧毁）与 `destroyed_at`（摧毁仿真时刻，床存在时为空）。床位置与几何归地图，拆除工作进度归玩家交互动作；成功破床时一次性更新状态、时刻并记录破床事件，重复结算不重复触发。摧毁者与具体原因归破床事件。具体拆除条件、同刻顺序及类型/编码仍待确定。

床定义为地图中的特殊对象，所属队伍/位置/占用区域归地图配置，动态存亡只由 `bed_state` 保存；空间查询结合两者，不在地形或实体中再保存独立的床存亡记录。若床占多格，各格子对应同一逻辑床；床周围防御方块归普通可变地形。具体尺寸/占用格式、碰撞与通行行为以及完整地图/实体格式仍待确定。

`upgrades` 采用 `upgrade_id -> level` 映射，只保存已购买项目；规则已定义但缺失的项目表示未购买，未知 ID 属于错误。一次性升级购买后记为 `1`，多级升级保存当前等级。最高等级、费用与效果归规则表，购买者/购买仿真时刻归事件；玩家属性与生成器效果依据当前等级计算。具体目录、类型/编码、对已有动作或生成器计时的作用方式仍待确定。

升级请求明确类型与目标等级，每次只购买一级；结算时重查购买资格、当前等级与资源。从购买者背包扣费、更新团队等级、记录事件作为一次完整结算，失败不扣费或改等级。同队多人并发购买同一目标等级时，按统一顺序只有一笔成功；后续因目标已达到而失败，不自动改买更高一级。具体排序机制、请求/反馈编码与完整购买资格待定，一次性请求去重仍按 0009 的独立请求身份设计。

`trap_queue` 采用有序陷阱实例列表，基础字段为 `trap_id`（本局唯一）、`trap_type`、`purchased_by` 与 `purchased_at`（成功购买仿真时刻）。允许同种重复购买、占多个队列位置并依次触发；每次成功购买生成不同 ID 的独立实例，不按种类合并或去重，仍逐笔检查资源/费用/资格/容量。队列显式保留顺序，不仅依靠时间戳排序。队列只保存待触发陷阱，已施加给玩家的临时效果仍归其 `effects`；同种重复入队不自动决定效果强度或时长叠加。

陷阱购买结算时检查资格、资源和队列约束，扣费、生成实例、追加队尾与记录购买事件一次完成，失败不扣费、不入队。触发只检查队首，不跳过选择后项；一次有效触发仅出队一个实例，同时产生对应效果或报警并记录事件，其余项保序。条件未满足则原队列不变，不提前消耗，也不在一次触发中连续清空队列。容量/计价函数与费用数值、商店与陷阱规则资格、冷却时长、免疫及字段类型/编码仍待确定。

共享冷却采用队伍级 `trap_ready_at`：当前时刻早于它则不触发/消耗，到时后仍检查触发条件；成功触发时与出队/效果/事件一并更新为当前仿真时刻加规则冷却时长。追加购买、队列变空、玩家死亡或丢床不重置。**用户要求上述整组规则标记为待与 Hypixel 核验，见规则参考 Q15；目前未验证。** 时长与具体时间表示仍待定，不能按未知即为零处理；标准初始化见下文。

用户明确陷阱不可主动移除，购买只能追加队尾；玩家不能删除、替换或重排已购队列项。购买者字段用于保留购买来源，不授予移除权限；队首正常触发消耗继续适用。此前提出的主动移除方案未采用，这项项目取舍不改写规则参考中的 Hypixel 历史记录。

床被摧毁后，已购队列保留且继续按序触发；满足条件仍可追加购买。触发区域继续使用地图配置的基地范围，不依赖床对象是否存在；范围几何/边界及编码仍待确定。

陷阱购买请求必须明确最高可接受费用 `max_cost`，缺失请求无效，不默认无限预算。结算时依当前规则与队列状态计算实际价格；不超过上限且其他检查通过时只扣实际费用，超过上限则失败、不扣费/入队，价格下降时也按较低实际价格成交。具体费用表示与并发排序仍待定，尚未将这一字段扩展为全部购买操作的通用协议。

队员名单从 `PlayerState.team_id` 派生，不重复保存独立成员名单；出生位置/朝向归地图配置。单个玩家死亡不清空团队升级和陷阱队列，其本生命临时效果仍按原规则清理。敌方能否获知升级/陷阱信息另按观测规则确定，床存续不能单独代替团队淘汰判定。

三组收尾方案已接受，逻辑设计见 [TeamState 总览](team-state.md)：首版单局固定阵容，只创建非空参赛队；有存活或等待复活者就继续参赛，全员淘汰才转为队伍淘汰，状态与成员计数派生且转换只记录一次事件。淘汰后保留原队伍记录/队列/截止时刻，但停止陷阱触发和购买；已施加效果、已生成实体按自身规则处理，世界胜负/同时全灭另定。

触发检查采用当前入侵者：队伍仍在参赛、队列非空、冷却可用且基地范围内存在通过队首规则资格的存活敌人时，按开局固定玩家顺序选一名触发者，一次检查只消耗一个队首。敌人持续停留在冷却结束后可再次触发，已在基地内时新购陷阱在后续满足条件的检查中也可触发；不保存进入/离开历史。作用对象由陷阱规则决定，牛奶/免疫、检查频率与全局排序另定，整组触发行为仍待 Hypixel 核验（Q15）。

标准新局采用床存在/摧毁时刻为空、空升级映射/空队列、`trap_ready_at = t0`（本局初始仿真时刻）。初始化校验玩家/队伍与地图床/出生点/基地范围引用，所启用规则的必需配置缺失不能默认零/关闭/无限；恢复快照保留原五字段、队列顺序/实例与截止时刻，世界重置不重置模型或训练进度。训练场景的预置覆盖接口与通用类型/编码另定。

## 已确定的死亡资源与统计规则

用户要求死亡时清空携带的铁、金、钻石和绿宝石，存活击杀者按规则接收，KD 等本局统计跨死亡与复活保留，见 [0004](decisions/0004-death-resources-and-statistics.md)。已接受的同批例外：击杀者本批次也死亡时，对应资源直接销毁，不在任一位置掉落，击杀归属与统计保留。没有有效击杀者时，死亡当刻位置安全则就地掉落，不安全则销毁；不回退最后安全位置。先固定本批所有死者转移前的四种资源，再统一清空、分别计算去向，避免循环转移。

安全位置按地形判定：在有效地图内、非虚空、该处能合法承载掉落物；不根据敌人是否存在或位置所属队伍改变判定。死亡结算取得死亡当刻位置并查询地图，不在 `PlayerState` 中重复保存独立的 `is_safe` 状态。

击杀归属已确定：敌方攻击直接致死时归于该攻击来源玩家；受击后坠落或环境死亡时，在时间窗口内归于最后一次有效敌方攻击者；无记录或超时则无击杀者。当前生命保存 `last_attacker_id` 与仿真时刻 `last_attacked_at`，复活时清空，本局统计继续保留。

归因窗口长度及端点、有效攻击判据、同一时刻的攻击排序、伤害来源映射字段、精确几何判据、批次具体类型/实现、特殊物品、容量及掉落物细节仍待明确。已确认有效归属下按接收者批次后生命处理：同批死亡/等待复活/淘汰则资源销毁不掉落，已复活存活则交当前新背包。窗口暂不设默认值。

统计与当前生命临时状态分别管理。用户已选择四项原始计数：`kills` / `deaths` 分别为普通击杀/死亡，`final_kills` / `final_deaths` 分别为最终击杀/死亡；同一次事件只计入普通、最终中的一类。总数由两类相加，比值由计数派生。四项均跨本局死亡和复活保留；零死亡展示、永久淘汰的时序边界及跨局汇总方式尚未确定。该规则尚未实现，不作为 Hypixel 完整线上机制的核实结论。

## 已确定的携带物品与购买进度

用户已接受 [0005](decisions/0005-inventory-and-progression.md) 的分类：一般购买的剑、弓、方块、药水等死亡清除且不转移/掉落；防具升级和已购剪刀保留购买记录、复活恢复；已购镐/斧死亡降一级，最低保留基础级，未购买者不自动获得。

`inventory` 表达当前生命实际携带物品，已选择物品数量表；四种资源也记录在同一表中，资源视图派生，不再维护独立钱包。表中数量为非负整数，不模拟具体槽位、快捷栏位次或拆分/合并堆叠操作。

容量已选择等效堆叠约束：将各物品数量除以其堆叠上限、向上取整后相加，不超过配置总容量。占用容量是派生值。总容量与各物品堆叠上限数值仍待确定，不能默认无限容量或绕过上限。

满容量处理已确定：购买按扣费并加入商品后的完整结果检查，不满足则整次失败、不扣费、不发货；地面拾取部分接收，余量原地保留；击杀资源尽量接收，余量在击杀者当前位置掉落，该处不安全则销毁余量。接收溢出与无有效击杀者时依据死亡位置的规则分别处理。

`AliveState` 显式保存 `held_item`，引用实际背包物品键或为空；切换物品会更新该选择。数量仍由背包唯一记录，属性由物品定义及变体提供，引用不额外生成物品或占用容量。

合法切换已选择瞬时完成，不单独耗时、不占持续动作通道，重复选择当前物品不产生变化。饮药、进食、拆块等需要持续手持对应物品，切走时中断交互并丢弃未完成进度，切回不自动恢复；未完成使用不提前扣物，已结算状态不回滚。切换不终止移动，也不重置物品/动作冷却。

当前物品仍有余量则保持手持，耗尽或移出背包时清空，不自动换物；无效切换被拒绝，原手持/交互保持且仍接受正常合法性检查。购买/拾取只更新背包，不自动改变选择，空手时也不自动选中。最后一件物品成功使用时，扣物、对应效果及清空手持作为一次完整更新，数量归零不使本次成功失效。

开局/复活生成本次装备后，选择配置的默认手持物品，首版为木剑，不继承上一条命的选择；配置校验须确认默认物品在当次背包中。其余初始装备、具体类型/空值、指令编码、同一时刻库存/切换/攻击/完成顺序仍待设计；其他参赛者能否看到手持信息另按观测规则确定。

`progression` 的四个基础字段已定为 `armor_tier`、`shears_unlocked`、`pickaxe_tier`、`axe_tier`，分别表达永久防具档位、剪刀购买标记及当前可恢复的镐/斧等级；未购工具为空，已购工具按死亡降级规则更新，不记录为历史最高等级。具体档位/材质/附魔和价格由规则表映射，类型、基础档与等级/空值编码待定。

实际穿着防具已选择由 `armor_tier`、规则表和团队升级派生，按头/胸/腿/脚分别映射，不维护独立可变装备表。穿着防具不进入普通背包或占用其容量，购买升级扣资源并更新档位，复活重新派生；首版不支持独立脱装/换装或防具耐久。具体材质/附魔/属性映射、伤害公式与观测仍待设计。

四种资源按 0004 单独结算，团队升级保留在 `TeamState`。容量参数、多种物品接收/争抢顺序、物品标识与属性键、工具等级映射、木剑以外的初始/复活物品及特殊物品细节继续待设计。

## 已确定的生命状态

用户已接受 [0006](decisions/0006-vitality-and-absorption.md)：`vitality` 分别保存 `health`（普通生命）和 `absorption`（剩余吸收生命）；最大生命由规则及相关效果计算。普通可吸收伤害先扣吸收、余量扣普通生命；仅耗尽吸收不死亡，普通生命耗尽触发死亡结算。复活时普通生命回满至生效上限，吸收清零。

数值与精度、吸收持续/到期、护甲和伤害类型、治疗与回血、临时效果具体类型/特殊效果合并、特殊死亡、保护与受击间隔、仅消耗吸收时的归因及同一时刻结算顺序仍待设计，不设未经核对的默认生命或药效数值。

## 已确定的临时效果死亡清理

用户选择药水、陷阱产生的本生命临时效果死亡时统一清空，旧效果不能延续或通过待处理事件作用到新生命。团队升级继续保留在 `TeamState`，复活后重新计算其作用，见 [0007](decisions/0007-temporary-effects.md)。

重复饮用同种药水已选择新效果覆盖旧效果：使用新等级，到期时刻为当前仿真时刻加新药水持续时间，旧剩余时间不叠加。该规则不自动覆盖药水/陷阱等其他来源的同类效果。

不同来源的速度、急迫等等级型增益已选择分别记录与计时，同时只取最高等级，不叠加强度；弱效果时间照常流逝，强效果结束后只恢复仍未到期的弱效果。当前生效等级由有效来源派生，团队升级仍归 `TeamState`。

周期型效果首次施加时，已选择等待一个完整周期后首次触发，`next_trigger_at` 初始化为施加仿真时刻加周期；非周期型效果不自动套用此规则。等级和周期不变时刷新，由新记录承接原下一次触发时刻，到期时刻仍按刷新规则重算；旧记录被替换，不重复触发或额外立即触发。到期时刻与下一触发时刻分别保留在 `expires_at` 与 `next_trigger_at`。

基础 `EffectState` 已确定六字段：`effect_id`、`effect_type`、`source`、`level`、`expires_at`、`next_trigger_at`，按实例记录来源与时序。具体类型、来源/标识格式、可选值编码及版本化协议尚未固定。特殊效果的额外数据和来源合并、等级/周期变化、多来源周期触发、到期顺序、吸收量重补、伤害揭隐及具体数值也仍待确定。

## 已确定的冷却与保护归属

用户选择主动冷却单独管理、保护复用 `effects`，见 [0008](decisions/0008-cooldowns-and-protection-effects.md)。`cooldowns` 按冷却组记录再次可用的仿真时刻；需要模拟的受击/复活保护使用各自 `EffectState`，不再重复保存保护截止时间或倒计时。

`cooldowns` 保存于 `PlayerState` 公共外层，每个冷却组在规则中指定死亡清除或跨死亡保留。清除时移除该组记录；保留时沿用原 `ready_at`，等待复活期间仿真时间照常推进，复活不重计时。组死亡策略不重复存入玩家记录；具体各组的选择仍待动作和物品规则确定，不自动设置默认方式。

保护使用自身的伤害与解除规则，不套用等级型增益取最高等级的算法。具体启用机制、共享冷却组、时长、适用伤害、主动攻击解除保护、各冷却组的死亡处理选择、额外数据及同一时刻顺序均仍待核对和设计，本次不默认任何数值。

## 已确定的动作双通道

用户选择 `movement` 与 `interaction` 两个执行通道，移动可与一项交互并行，交互通道同一时刻只执行一项操作，见 [0009](decisions/0009-movement-and-interaction-channels.md)。瞬时转向不占用持续动作通道；两个通道仍由引擎统一结算，不重复推进时间。

正常决策轮未更新某通道时，用户已选择保持当前持续动作，直到完成或被中断；保留原实例和进度，不重新开始计时。完成的动作不自动重新发起，购买和物品消耗等一次性结算不重复。

新指令规则已定：与当前持续动作的种类/目标/参数相同则保持进度；不同且合法则中断替换指定通道、丢弃未完成进度；无效则拒绝新指令，原动作继续接受正常合法性检查。另一通道不受影响，不自动排队，已完成结算不撤销。一次性操作的去重另按请求身份设计，不能仅比较购买内容。

执行中目标消失、目标玩家当前生命结束，或不再满足动作要求的距离/朝向时，中断对应动作并丢弃未完成进度；即使只是暂时失效也不暂停保留，条件恢复后必须重新下令并创建新实例。其他通道按自身条件继续。只检查该动作实际要求的条件，不改变移动与朝向独立的规则；动作定义中的正常冷却等待另行处理。检查时序、精确边界与未列中断条件仍待设计，反馈不得额外泄露隐藏目标信息。

[W06 拆建规则](decisions/0013-world-engine-and-state.md)已明确：多人拆块独立累计进度，首次合法移除后其余动作中断；拆块在引擎内部绑定方块实例，同格同材质重建也不能继承旧进度/完成事件。已进入结算的拆/放候选逐笔检查最新地形，已拒绝请求不自动恢复。具体实例编码及外部目标消息格式仍待定。

物品结算时点已定：饮药/吃金苹果完成时扣物并施加效果；方块成功放置时扣除；投掷/发射消耗品在成功生成世界实体时扣除，不等待命中。主动取消、替换或失败不提前扣除；已生成的方块/实体/效果不回滚也不退物品。死亡仍按既定物品分类清理，购买沿用成功同时扣费/发货的规则。

死亡时立即终止并清空两个动作通道，丢弃未完成进度，记录死亡这一结束原因；复活后通道为空，策略需重新下达指令，不自动恢复旧动作。旧动作实例及其尚未提交的完成事件不能作用于新生命。已放置方块、已发射实体按自身世界规则继续，不因来源玩家死亡而回滚；本生命临时效果仍按 0007 清理，冷却按 0008 的组规则处理，复活空间初始化按 0010 执行。具体组选择、出生保护边界及同一时刻死亡/完成顺序继续待设计。

`spatial` 表达真实空间状态，移动通道表达主动移动意图与执行信息；交互通道保存继续操作所需的目标、进度与阶段等数据。基础 `ActionState` 已确定 `action_id`、`kind`、`target`、`params`、`started_at`、`progress`、`phase` 七字段。动作语义由 `kind + target + params` 表达；保持时不重置实例身份、开始时刻和进度。

`ActionState` 是引擎维护的运行状态，不是允许外部策略任意写入的指令对象；执行身份、开始时刻、进度和阶段由引擎更新。具体类型、动作目录/耗时、语义比较、空通道与保持/取消/去重编码、故障反馈的完整原因码、未列中断与条件检查时序/边界、未列动作消耗/耐久及同一时刻顺序仍待设计。

## 设计约束

- 由中央调度统一推进世界；不能因多位 Agent 依次请求而重复推进同一个 tick。
- 世界状态与参赛者观测分离；合法动作、奖励、info 和错误不能意外泄露隐藏目标。
- seed 只是复现条件之一；还需要同规则、同配置、同策略输入或同动作序列。
- 墙钟超时与仿真时间区分；网络与画面刷新不驱动规则时间。
- 格式落定后将机器可检查的定义放入 `schemas/`，再增加相应固定样例与行为测试。
- 普通死亡等待期间破床不取消本次复活已按 0010 采用；来源为 BW-LIFE-04 官方历史，与 Blockyard 实现不同。现行线上完整边界仍待核对，同一时刻破床/死亡排序仍待设计。

## 候选接口

调研中提出了 `reset(seed)` / `step(actions)` 形式，可供下一轮设计比较。当前没有实现这两个方法，也没有声明 PettingZoo 兼容性。

若采用该形式，必须先写清 observations、rewards、terminations、truncations、infos 的键集合及复活期间是否保留 Agent，避免只做到函数签名相似。
