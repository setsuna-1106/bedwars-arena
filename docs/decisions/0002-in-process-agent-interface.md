# 0002：首版采用 Python 进程内策略接口

日期：2026-10-25  
状态：用户已接受的设计决策；接口与运行链路待实现。

## 背景

项目需要让外部决策算法读取玩家观测并提交动作。当前规则引擎和对局接口尚未实现，观测、动作和时序也仍需设计。

用户选择先采用 Python 进程内调用，同时让接口具备转向独立进程的条件。这一选择确定接入方式，不确定空间模型、玩法参数、动作字段、仿真底座或网络框架。

## 选择

- 首版策略作为 Python 对象，在对局所在进程中运行；由 Runner 调用策略并收集动作。
- 一局世界状态由引擎持有并修改；只有 Runner 调用引擎的推进入口。策略、观测接口和渲染不能自行推进世界。
- 观测与动作采用明确的数据契约，后续独立进程适配器复用其语义。通信不参与规则计算。
- 独立进程与网络接入作为后续扩展，本次不引入进程管理、通信服务或协议依赖。

## 为独立进程接入保留的边界

### 观测是独立数据

策略只接收符合可见性规则的观测数据，不接收世界对象、引擎、Runner 或其他玩家策略的引用。观测中的嵌套容器也不能与引擎状态共享可变对象；策略修改或保留观测，不应影响真实状态或其他玩家的观测。

同一决策轮的观测基于同一世界状态生成，在调用策略期间不推进世界。首版逐个调用策略时，调用先后不能让后调用者看到前一策略的动作结果。

### 动作是可转换为消息的值

观测和动作的数据契约应能显式转换为 JSON 兼容的值：空值、布尔值、整数、有限浮点数、字符串、列表和字符串键对象。不把函数、回调、生成器、引擎实体或任意 Python 对象身份作为动作语义。

内部可以使用有类型的数据对象，但需要明确其值表示。进程内调用不要求每轮实际进行 JSON 编解码；具体数据类、字段、消息格式与版本号尚未确定。

策略返回的动作需要校验并转换为引擎拥有的数据后再保存或执行，避免策略继续持有可变引用而改变待执行动作。格式校验与玩法合法性校验分别由接口层和引擎负责。

### Runner 统一推进

Runner 为同一决策轮准备观测、调用策略、收集并校验动作，再按契约调用引擎推进。一次策略调用或一次未来通信请求不自动推进世界。

决策轮与仿真 tick 分别标识，不预设一轮等于一个 tick；具体耗时、收集对象与结算顺序仍由时序契约确定。墙钟耗时与仿真时间分开。

### 行动可以追踪

记录需能关联对局、策略身份、决策轮与对应仿真时刻，并保存提交动作、实际执行动作及其处理结果。若发生拒绝或替代，不能只保存最终动作而丢失原因。

规则、地图、配置、策略版本及随机性信息应一并追踪。消息封装和记录字段待后续契约确定；本次不声明已有回放或复现实现。

## 调用职责

| 部分 | 职责 |
| --- | --- |
| 引擎 | 持有世界状态，验证玩法合法性，执行动作与更新状态 |
| 观测与接口 | 按信息边界导出独立观测，校验和转换动作数据 |
| Runner | 组织决策轮、调用策略、统一推进并记录结果 |
| 策略 | 根据观测和自身记忆返回动作 |
| 未来进程适配器 | 收发相同语义的数据，管理算法进程，不重复实现规则 |

## 收益与限制

进程内调用便于调试和调整契约，首版不承担通信与部署成本；接口边界允许后续增加独立进程适配器。

首版没有进程隔离，不承诺可靠地强制终止卡死策略或隔离原生库崩溃。策略异常、软超时与必需动作包缺失时的 Runner 备用取消及故障记录方向已按 [0015](0015-world-schedule-replay-failures-and-training.md) 采用；具体原因码/API 仍待实现。

本次不固定 `reset`、`act`、`observe`、`step` 等方法的正式签名，也不声明 PettingZoo 兼容性。仿真底座、独立进程协议和网络框架继续待选。

## 后续验收

以下是实现时需要增加的验证，不是已经通过的测试：

- 修改观测及其嵌套内容，不影响引擎状态或其他玩家观测。
- 动作返回后，策略继续修改原对象，不改变已接收的动作。
- 观测和动作可转换为约定的消息值并往返还原其语义。
- 同一决策轮调用多位策略，不会因调用次数而重复推进世界。
- 记录可定位每轮提交、拒绝或替代及实际执行的动作。
- 策略异常按契约处理，仿真时间不受函数调用或画面刷新速度驱动。

观测和动作字段、完整消息格式、性能目标等仍待落实；决策轮、策略生命周期及异常处置的已采用方向见[接口与时序草案](../contracts.md)和 0015。
