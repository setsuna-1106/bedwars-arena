# 0011：TeamState 基础结构与数据归属

日期：2026-10-26  
状态：逻辑设计已收尾；类型/JSON 编码、参考档案、纯状态转换与事件排序基础已按 [0012](0012-team-core-types-and-ordering.md) 实现。完整世界/空间/效果应用仍未完成，共享冷却与触发机制继续待 Hypixel 核验（Q15）。

## 已确定

用户在原四字段基础上接受新增 `trap_ready_at`，当前五个基础字段为：

| 字段 | 职责 |
| --- | --- |
| `team_id` | 队伍标识，用于与玩家的队伍关联对应 |
| `bed_state` | 本队床的存续状态 |
| `upgrades` | 已购买的团队升级及等级 |
| `trap_queue` | 待触发的陷阱队列 |
| `trap_ready_at` | 本队下一次允许触发陷阱的仿真时刻；共享冷却设计已采用、待 Hypixel 核验 |

字段职责、床状态、升级映射与陷阱结构已确定；后续类型/编码和纯转换实现见 0012 与 [core](../../src/bedwars_arena/core/)。内部 TeamState v1 不等同冻结的外部策略 API 或完整世界引擎。

用户已接受队伍生命周期、陷阱触发条件、标准开局初始化三组收尾方案，汇总见 [TeamState 已确认设计总览](../team-state.md)。本次收尾限于逻辑数据归属与已列机制，不将参数、通用类型、全局时序或现实核验标为完成。

## 床状态

用户接受 `bed_state` 使用以下两个基础字段：

| 字段 | 含义 |
| --- | --- |
| `status` | 床存在或已摧毁；v1 编码为 `present` / `destroyed` |
| `destroyed_at` | 摧毁的仿真时刻；床存在时为空，摧毁时记录该时刻 |

配套数据归属与结算约束：

- 床的位置与几何信息读取地图配置，不重复放入队伍动态床状态。
- 拆除工作进度保存在执行玩家的交互动作中，沿用动作保持与中断规则。
- 成功破床时，一次性更新状态与摧毁时刻，并记录破床事件；对同一张床的重复结算不重复触发破床事件。
- 摧毁者与具体原因记录在破床事件中，不重复作为 `bed_state` 字段。

这些字段保存引擎状态，不决定智能体能看见哪些床信息。拆除空间条件尚未实现；同刻破床/死亡已按 0012 的平台排序约定落地，不声称 Hypixel 内部顺序已验证。

## 床与地图的关联

用户接受将床定义为地图中的特殊对象：

| 数据 | 归属 |
| --- | --- |
| 床所属队伍、位置、占用区域 | 地图配置 |
| 床是否存在、摧毁时刻 | `TeamState.bed_state` |
| 床周围的防御方块 | 普通可变地形 |

空间查询结合地图配置与 `bed_state` 判断床是否存在，不在地形或实体中再维护另一份可独立改变的床存亡状态。若床覆盖多个格子，这些格子对应同一张逻辑床；具体尺寸与占用区域格式仍待确定。

这次选择确定床的配置与动态状态如何关联，不补定床的碰撞形状、通行行为、放置或拆除条件，也不冻结完整地图与实体格式。

## 团队升级映射

用户接受按升级类型保存已购买等级：

```text
upgrades[upgrade_id] = level
```

- 仅保存已购买项目。当前规则目录中存在、但映射中缺失的升级表示未购买；未在规则目录中定义的升级 ID 属于错误，不能按未购买处理。
- 一次性升级购买后记为 `1`，多级升级保存当前购买等级。
- 最高等级、费用与实际效果由规则表定义，不复制进队伍状态。
- 购买者与购买仿真时刻归购买事件，不在升级映射中保存另一份历史。
- 玩家属性与生成器效果依据当前升级等级计算，沿用团队升级来源唯一的约束。

本节确定逻辑表示；ID/等级编码和带证据状态的参考目录已在 0012 实现，完整现服价格与升级对已有动作/生成器计时的作用仍待完成。

## 团队升级购买结算

用户接受指定目标等级的购买方式：

- 购买请求明确升级类型与目标等级，每次只购买一级。
- 结算时重新检查购买资格、当前等级与购买者资源，不仅依赖提交请求时的状态。
- 从购买者背包扣费、更新团队等级与记录购买事件，作为一次完整结算；失败不扣费、不改变等级。
- 同队多人同时请求同一目标等级时，按统一顺序结算。第一笔成功后，后续请求因目标已经达到而失败，不自动改买更高一级。

例如，两人都请求购买保护 II，只有一笔成功，最终仍为 II，仅成功购买者支付费用。稳定事件排序与去重基础见 0012，完整外部请求/反馈协议与商店空间资格仍待确定；一次性请求去重继续沿用 [0009](0009-movement-and-interaction-channels.md) 的独立请求身份边界，不把不同购买请求仅按内容去重。

这是本项目的交易语义设计，不作为现行 Hypixel 并发购买行为的核实结论。

## 陷阱队列基础结构

用户接受 `trap_queue` 使用有序的陷阱实例列表，每个实例包含四个基础字段：

| 字段 | 含义 |
| --- | --- |
| `trap_id` | 本局唯一的陷阱实例标识 |
| `trap_type` | 陷阱种类，对应规则目录 |
| `purchased_by` | 购买者的玩家 ID |
| `purchased_at` | 成功购买的仿真时刻 |

- 每次成功购买生成独立实例，用于准确引用、触发结算与事件关联。用户选择 B，允许同种陷阱重复购买并占据多个队列位置，依次触发；各实例具有不同 `trap_id`，不合并为一个种类计数。
- 队列显式保存顺序，不仅依靠购买时间戳排序，避免同一仿真时刻购买时无法确定列表顺序。
- 队列保存待触发陷阱；已施加给玩家的临时效果仍归玩家 `effects`，不作为待触发实例继续保存在队列中。

本节确定实例与列表结构；入队/触发规则见下文，具体字段类型、ID/种类编码和内部纯函数已按 0012 实现，外部动作消息与完整世界集成另定。

## 陷阱入队与触发

用户接受以下规则：

- 购买成功追加到队尾。结算时检查购买资格、资源与队列约束；扣费、生成实例、入队与记录购买事件一次完成，失败不扣费、不入队。
- 按队列顺序触发，只检查队首，不跳过它选择后面的陷阱。
- 一次有效触发仅消耗队首一个实例；出队、产生该陷阱对应的效果或报警、记录触发事件作为一次完整结算，其余实例保持顺序。
- 触发条件未满足时保留原队列，不提前消耗；一次触发不连续清空队列。

用户随后明确：陷阱无法主动移除，购买操作只能向队尾追加。不提供玩家删除、替换或重排已购陷阱的操作；此前提出的购买者主动移除方案未采用。已确认的队首触发消耗规则继续适用，不能把不可主动移除解释为触发后仍保留队列项。`purchased_by` 继续保留购买来源，不表示购买者拥有移除权限。

同种重复购买仍逐笔接受购买资格、资源、费用上限与队列容量检查，不表示容量无限。各实例按队列顺序分别参与后续触发；消耗一个不一并消耗同种其他项。允许重复入队不额外决定同刻触发次数，也不自动使效果强度或持续时间叠加。

具体容量、计价函数与费用数值、商店购买资格、队首陷阱的规则资格、冷却时长与牛奶等免疫交互仍待确定。共享冷却及持续停留/多人选择机制见下文，已采用但待 Hypixel 核验；排序基础见 0012，完整世界阶段处理器另定。这里记录已采用的项目设计，不作为现行 Hypixel 完整陷阱机制的核实结论。

## 队伍共享陷阱触发冷却（已采用、待 Hypixel 核验）

用户接受整队共享一个陷阱触发冷却，在 `TeamState` 保存 `trap_ready_at`：

- 当前仿真时刻早于 `trap_ready_at` 时，不触发、不消耗陷阱；达到该时刻后仍须满足其他触发条件。
- 成功触发时，队首出队、对应效果/报警、事件记录与冷却更新一并结算；`trap_ready_at` 更新为当前仿真时刻加规则规定的冷却时长。
- 追加购买、队列变空、玩家死亡或丢床均不重置该时刻。
- 冷却时长由规则配置，具体数值未定，不能按未知即为零处理。

**核验标记：上述整组共享冷却规则是已采用的项目设计，尚未与 Hypixel 规则检验。** 用户此次要求保存待核验标记，本次未开展线上规则验证。核验清单见规则参考 [Q15](../rules/hypixel-bedwars.md)，需要确认：

1. 冷却是否整队共享，是否存在按陷阱类型或入侵玩家区分的机制。
2. 开始计时的时点、适用陷阱及具体时长，不能混用陷阱效果持续时间。
3. 追加购买、空队列后重新购买、玩家死亡、丢床是否改变冷却。
4. 冷却期间多人同时入侵，以及到期时敌人持续停留的实际触发行为。

标准初始化与全队淘汰处理见下文，时间类型/编码已见 0012，具体规则资格与免疫交互另定。核验标记不表示暂停本次采用，也不表示任何 Hypixel 一致性测试已经通过。

## 陷阱触发条件（已采用、待 Hypixel 核验）

用户接受检查当前合格入侵者的方式：队伍仍在参赛、队列非空、当前时刻达到 `trap_ready_at`，且地图基地范围内有通过队首陷阱规则资格检查的存活敌方玩家时，进行触发结算。

- 敌人持续停留时，冷却结束后可在后续检查中再次触发，不要求重新跨越基地边界。
- 敌人已经在基地内时新购陷阱，也在下一次满足条件的检查中参与触发。
- 多人符合条件时，按开局配置中固定的玩家顺序选一名触发者。触发者与效果接收者分别处理，具体作用对象由陷阱规则定义。
- 每次检查只结算一个队首实例，不连锁检查剩余队列；不新增上一轮入侵者集合或进入/离开历史字段。

上述行为作为项目设计采用，继续标记待 Hypixel 核验（Q15）。牛奶对触发、消耗和效果的具体影响、范围几何、检查频率及与移动/死亡/购买的排序基础见 0012，完整世界阶段处理器另定。

## 丢床后的陷阱行为

用户接受床被摧毁后陷阱继续运作：

- 已购买的队列保留，继续按原顺序参与触发。
- 满足购买条件时仍可向队尾追加购买，床被摧毁本身不禁止购买。
- 触发区域继续使用地图配置的基地范围，不依赖床对象是否存在。

基地范围的具体几何/边界与地图字段编码尚未确定；全队淘汰后的停用与记录保留见下文。本节不新增对 Hypixel 线上丢床后陷阱行为的核实结论。

## 陷阱购买费用上限

用户接受陷阱购买请求必须携带最高可接受费用 `max_cost`：

- 结算时根据当前规则与队列状态计算实际价格。
- 实际价格不超过费用上限，且资源与其他条件满足时成交，只扣实际价格。
- 实际价格超过费用上限则失败，不扣费、不入队。
- 缺失费用上限的请求无效，不默认无限预算。

队友先购买导致价格上涨时，本次请求不会超出其声明的费用上限；价格下降时按较低实际价格成交。具体计价函数、费用数值、并发排序以及费用字段的类型/编码仍待确定。本次接受范围为陷阱购买请求，不自动把 `max_cost` 扩展为全部购买操作的已定协议字段，也不在陷阱实例中重复保存请求预算。

## 队伍生命周期

用户接受首版单局固定阵容，本局启用的每支队伍至少一名玩家；地图预留但未启用的队伍不创建 `TeamState`，中途加入/换队属于后续扩展。

- 至少一名成员处于 `AliveState` 或 `RespawningState`，队伍仍在参赛；全体成员均为 `EliminatedState` 才淘汰。全队等待复活不能被当作队伍淘汰，床状态也不单独决定淘汰。
- 参赛/淘汰状态与成员计数从玩家状态派生，不新增独立可变字段，维持五字段结构。
- 从参赛转为淘汰时记录一次队伍淘汰事件；保留队伍记录、床状态、升级、陷阱队列与原冷却截止时刻，供快照/回放/检查，不改写为暂停的剩余冷却。
- 淘汰队伍停止陷阱触发且不能购买；已经施加的玩家效果、已经生成的世界实体继续遵守各自规则，不因本次队伍处理额外删除。

最终胜负与同时全灭由世界终局规则另定，本节不代替 `WorldState` 的结果判定。

## 标准开局初始化

用户接受标准新局以本局配置的 `team_id` 创建队伍：床存在、摧毁时刻为空，`upgrades` 为空映射，`trap_queue` 为空列表，`trap_ready_at = t0`（本局初始仿真时刻），表示初始没有尚未结束的触发冷却。v1 使用 present/destroyed、JSON null 与整数 tick，见 0012。

- 初始化校验玩家/队伍关联与地图中的床、出生配置和基地范围引用；不将未启用地图槽位当作参赛队伍。
- 启动完整对局前必须具备所启用规则所需的容量、计价与冷却时长等配置，缺失不能按零、关闭或无限处理。
- 恢复快照保留原五字段、实例 ID/顺序与冷却截止时刻，不重走新局默认值。
- 预置升级/陷阱或无床训练场景的覆盖接口另行设计；世界初始化与模型/优化器/跨局训练状态分离。

## 数据归属

- 队员名单从 `PlayerState.team_id` 派生，不在 `TeamState` 再维护一份独立成员名单。
- 出生位置与初始朝向继续读取地图配置，沿用首版每队一个固定出生点的选择，不重复写入队伍动态状态。
- 团队升级与陷阱队列归队伍；单个玩家死亡不清空这些状态，作用到玩家的本生命临时效果仍按原规则清理。
- 玩家穿着防具与其他团队升级作用按当前队伍状态和规则查询，不在每个玩家保存独立的团队升级真值。

这是引擎完整状态的组织方式，不表示敌方智能体可以获得完整的升级或陷阱信息，观测范围仍待设计。

## 与玩家生命周期及规则资料的关系

床的存续与玩家当前生命分别表达。已接受的普通死亡规则继续适用：死亡结算时床存在则获得本次复活资格，等待期间丢床不取消该次复活；不能直接从床已毁推导全队已淘汰，见 [0010](0010-player-lifecycle-branches.md)。

玩法资料参考 [BW-LIFE-01/02/04、BW-UPGRADE-01、BW-TRAP-01](../rules/hypixel-bedwars.md)。已接受的结构、归属与交易语义不补定升级费用、效果、陷阱容量、触发范围或具体事件排序，不将社区候选值直接当作已采用参数。

## 后续验收

以下是实现时需要增加的验证，不是已通过的测试：

- 队员名单与玩家队伍关联一致，不因重复维护列表而产生不同成员集合。
- 玩家死亡/复活不误清空团队升级或待触发陷阱队列，本生命效果仍按自身规则清理。
- 出生配置与团队升级来源唯一，玩家查询使用对应队伍和地图数据。
- 床被摧毁不错误地取消已经获准的待复活玩家，队伍淘汰判断与玩家生命状态分别处理。
- 床存在时摧毁时刻为空；成功破床同时更新状态、记录仿真时刻并产生一次破床事件，重复结算不重发事件。
- 拆除进度沿用玩家交互动作的保持与中断规则，床的几何配置、破床事件中的来源与原因不在队伍动态床状态重复维护。
- 床的空间查询使用地图配置与队伍床状态；摧毁后不因另一份独立存亡记录而仍被查询为存在。若覆盖多个格子，各格子均关联同一逻辑床，防御方块按普通可变地形处理。
- 升级映射只保存已购买项目及等级；已定义但未购买的项目与未知升级 ID 分别处理，一次性升级使用等级 `1`，具体等级边界按规则表验证。
- 升级费用/效果来源于规则，购买者/时刻来源于购买事件；玩家与生成器查询不重复维护另一份团队升级真值，保存/恢复后仍能依据当前等级计算效果。
- 升级请求按指定目标等级每次只购买一级，结算时重查资格/当前等级/资源；成功时扣购买者资源、更新团队等级与记录事件一并完成，失败不扣费或改等级。
- 同队并发请求购买同一目标等级时只有一笔成功，后续不扣费或自动购买下一等级；具体先后次序按后续确定的统一排序机制验证。
- 陷阱实例保存四个已定字段，使用本局唯一 ID 区分不同购买实例；相同仿真时刻购买的实例仍能显式保留队列顺序，保存/恢复不因按时间戳重排而改变该顺序。
- 同种陷阱可占多个队列位置，每笔成功购买有独立实例；保存/恢复不按种类合并或去重。正常触发只消耗队首一个，其余同种实例保留，购买仍受费用/资源/资格/容量约束。
- 待触发队列与已经施加给玩家的临时效果分别保存，不把生效效果当作仍待触发的队列项。
- 陷阱购买重查资格/资源/队列约束，成功时扣费、生成实例、追加队尾与记录事件一并完成，失败无扣费或入队。
- 陷阱购买必须提交费用上限；按结算时实际价格检查，超上限或缺失上限不扣费/入队，低于上限时只收实际费用。并发购买引起的变价不绕过该约束。
- 玩家不能主动删除、替换或重排已购陷阱，购买仅追加队尾；购买者身份不授予移除权限，非法队列操作不改变原队列。队首正常触发仍按规则消耗。
- 陷阱触发仅检查队首；条件未满足不消耗或跳过，一次有效触发只出队一个实例并同时产生对应结果/事件，其余项保序，不因同一次触发连续清空队列。
- 床被摧毁不清空或重排陷阱队列，不单独禁止后续触发/追加购买；触发使用地图基地范围，不因床对象不再存在而失效。全队淘汰后保留原记录与队列，但停止触发和购买。
- 按已采用的共享冷却设计验证：截止时刻前无触发/消耗，到时后仍检查触发条件；成功触发同步更新 `trap_ready_at`，购买/空队列/玩家死亡/丢床不重置。快照保存并恢复原截止时刻；这些项目行为测试不能替代 Q15 的 Hypixel 对照核验。
- 队伍生命周期由非空固定阵容派生：存活/等待复活者维持参赛，全员淘汰才转为淘汰并记录一次事件，不额外删除已施加效果或世界实体。
- 持续停留者到冷却结束后可再次参与触发，新购陷阱也按当前入侵者检查；多人合格时按开局固定玩家顺序选触发者，一次检查不连锁消费。
- 标准开局为床存在/摧毁时刻为空、空升级/队列、`trap_ready_at = t0`；快照恢复不重置这些值或模型训练状态，缺失必需配置不得静默填默认。
- 保存/恢复队伍所需状态后，按后续确定的规则保持一致，参赛者观测不泄露隐藏队伍信息。
