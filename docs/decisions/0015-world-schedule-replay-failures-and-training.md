# 0015：W10–W12 世界赛程、恢复、故障与训练衔接

日期：2026-10-27。**状态：用户已整组采用以下设计；完整世界引擎、处理器与训练接口尚未实现。**

本决定承接 [W10 已接受部分](0013-world-engine-and-state.md)和 [W09](0014-w09-world-objects.md)，并确定观测、奖励和持续学习的首版衔接方向。用户采用的是文中标出的平台规则和实验候选，不代表这些细节均已在 Hypixel 现服核实。正式接口字段、规则表和实现需在此基础上继续细化。

## 1. W10：赛程与同 tick 事件

### 1.1 两个显式赛程档案

前期严格二维 A 实验和将来 B 正式物理分别建立档案，均需由对局配置显式选择；不因地图是两队或四队就自动假定属于 Hypixel 的独立 4v4。具体档案标识与配置编码待落实。

06:00–50:00 为 [BW-TIME-01](../rules/hypixel-bedwars.md) 的[社区候选时间表](https://breezil.github.io/Breezil-Hypixel-Utils/reference/bedwars/game)，不是所有模式现服已核实规则。45:00 是把该候选表的 40:00 与 [2025 官方第二条龙间隔](https://hypixel.net/threads/bed-wars-v1-9-3-new-settings-menu-other-changes.5828709/)相结合得到的**推导**；[2026 官方修复](https://hypixel.net/threads/bed-wars-v1-11-dreamfeast.6003011/)也提到 Sudden Death 5 分钟后的额外龙，但不独立证实前表对所有模式适用。

作为显式选用的社区实验参数，钻石 I/II/III 周期分别为 30/24/12 秒，绿宝石分别为 56/40/28 秒；首次生成实验性等待 I 级一个完整周期。周期来自同一[社区表](https://breezil.github.io/Breezil-Hypixel-Utils/reference/bedwars/game)，**首次等待是平台选择**。生成数量、容量、范围及铁/金参数仍需明确配置，不能因本方案被采用而假设已核实。

A 档案关闭龙是一项明确的实验简化，不称为完整 Hypixel；B 档案只有在地图、龙处理器及所有必要参数齐备时才能创建。启用生成器升级的档案须在地图中明确提供对应生成器和等级定义；要在没有某类生成器的场景训练，应显式选择关闭该类事件的另一档案。若配置启用事件或实体而缺定义/处理器，初始化报错，不能运行时跳过。独立 4v4 的历史边界收缩另做档案，不套用上述龙档案。

### 1.2 固定阶段与同 tick 顺序

| 事项 | 已采用规则 |
| --- | --- |
| 生成器等级升级 | 放在 0 阶段既有到期清理之后、25 阶段生成之前。变更后保留原 `next_spawn_at`，更新计划实例 ID，并为原时刻排新计划；旧计划按 W07 失效。 |
| 升级和生成同 tick | 0 阶段先升级，25 阶段按升级后的产量/容量生成；原定生成时刻不变，下一周期用新等级。先生成新计划、再在后续 25 阶段执行，不向当前或已结束阶段投递。 |
| 全局破床 | 50 阶段先以 W06 顺序逐笔处理已完成的合法玩家破床，再由全局事件摧毁剩余床；已毁的床不再重复产生破床事实。全局摧毁不归功给玩家或队伍。 |
| 同 tick 死亡 | 60 阶段读取 50 阶段更新后的床；之前已获准的复活不因本次全局破床撤销。 |
| 同 tick 多个系统事件 | 按固定档案事件顺序，再用稳定 ID 打破剩余并列；不按线程、容器迭代或请求到达时间排序。 |
| Game End 和自然胜负 | 90 阶段先依既定规则判 0/1 支参赛队伍；已有自然结果时无需再产生 Game End 胜负。仍有多队时才执行 Game End 比较。已到期但被自然结果取代的任务标为内部跳过，不生成第二个终局。 |

这些是平台时序约定，不声称复刻 Hypixel 服务端同刻顺序。

### 1.3 B 档案的龙：首版实验机制

40:00 为当时每支仍参赛队伍在地图配置的合法出生点生成一条龙；45:00 为当时每支仍参赛队伍再生成一条，第一条是否仍存在不影响第二次生成。这里的“仍参赛”按已定队伍规则：队内至少一人存活或等待复活。首批数量以及此资格解释是平台实验选择。

赛程在 0 阶段发出生成任务，实体在同 tick 45 阶段创建，下一 tick 30 阶段开始运动；龙作为独立实体，来源队伍后来淘汰不会自动删除已创建的龙。无目标时按规则等待，不因队列暂时为空停止模拟。

首版龙选择距离最近的可攻击敌方存活玩家，距离相同按固定玩家顺序选择；碰撞/地形变化按实体规则进入 30/45 阶段，伤害和死亡进入 60 阶段，地图保护仍有效。龙的归属队伍不自动等于某个玩家击杀者，具体击杀归属继续按已有规则判断。目标选择及此阶段挂接是实验方案，不声称 Hypixel 龙 AI 已核实。出生位置、尺寸、移动、索敌范围和视线条件、伤害与冷却、生命/寿命、对地形的破坏范围和可破坏材料、接触与命中规则均须在龙档案中显式给定；欠缺时不能启用。龙死亡后不自动补生，首版只按上述两个固定时刻安排两批。

## 2. W10：Game End、结果与训练边界

### 2.1 Game End 已采用比较

90 阶段仍有至少两支参赛队伍时，只比较这些队伍，依次按：

1. 该队 `AliveState` 与 `RespawningState` 的人数，人数多者优先；
2. 人数相同则比较该队由玩家取得归属的敌方床摧毁数，多者优先；
3. 仍相同则这些并列队伍构成平局，不以颜色、队伍 ID 或随机数破平局。

若只有一个最高分队伍则其获胜；若两个或以上最高分队伍并列，则世界结果是平局，保留并列队伍与比较依据。全局定时摧毁不加破床数。破床队伍计数存入 `WorldState.execution` 的比赛统计，作为用于裁决的单一可恢复真值，在 50 阶段与有归属的破床一起提交；不复制进 `TeamState`，也不依赖外部日志重算。训练场景从零统计开始，不凭预置的已毁床虚构破床历史。

[2025 年 Hypixel 工作人员说明](https://hypixel.net/threads/important-fix-the-game-end-logic.5984093/)证实当时将存活队员数置于破床数之前；`RespawningState` 如何计入、完整同分链、并列平局及当前各模式是否一致仍未核实。上述顺序后半部分是**平台实验规则**，有证据更新后应新增规则版本而非悄悄改变旧回放。

### 2.2 世界结果与 Runner 反馈

| 情形 | 世界 `result` | 训练反馈 |
| --- | --- | --- |
| 对战获胜或平局 | `match_win` / `match_draw`，记录结束 tick、原因、胜队或并列队 | `terminated=true` |
| 单队任务成功/失败 | `task_success` / `task_failure`，记录任务及指定玩家，不虚构对战胜队 | `terminated=true` |
| 仅到达外部训练时限 | 保持 `result=null`；世界本身仍未自然结束 | `truncated=true`，无胜负 |
| 自然结果和外部时限同 tick | 保留实际自然结果，标记同时到达时限 | `terminated=true`、`truncated=true`；主要结束原因仍为自然结果 |
| 引擎故障 | 不伪造自然结果或截断结果 | 单独返回故障，停止该运行 |

两个标志同时为真表示两个事实都发生；学习端对真正终局按终局处理，不能仅因为 `truncated=true` 误作非终局 bootstrap。这个编码符合 [Gymnasium TimeLimit 的表达能力](https://gymnasium.farama.org/_modules/gymnasium/wrappers/common/)，但本方案不因此引入 Gymnasium。最终观测与可见反馈继续过滤隐藏信息。

Runner 时限从本次 episode 起始边界起算，保存 `start_tick`、正整数 `max_ticks` 和实际进度；每个完整 tick 后检查。精确恢复保留原基准与剩余时长。已截断的 episode 已结束；若从其世界快照继续，显式创建新的续接 episode、记录来源和新时限，不把两段伪装成一个未中断 episode。

### 2.3 单队训练目标

首版支持两类，均显式指定玩家、参数和任务档案：

- **到达区域**：在 90 阶段，指定存活玩家的水平中心处于配置的半开矩形 `[xmin,xmax) × [zmin,zmax)`；B 另要求脚底 `y` 在配置的 `[ymin,ymax)`。区间须有限且上下界严格递增，A 不使用高度条件。
- **当前持有数量**：在 90 阶段，指定存活玩家背包中的指定物品数量 `>=` 配置的正整数门槛。离开存活分支时该条件为假，不把之前短暂持有算作当前达标。

永久淘汰为失败；普通死亡及等待复活继续；首次判断为 tick 1，同刻失败优先，均保持已有决定。其他目标类型以后扩展，不从这两项自动推断。

## 3. W11：快照、随机源与重放

1. **保存边界。** 对外快照只取 tick 0 或完成 90 阶段并发布的完整 tick 边界。引擎处理到一半时不发布中间快照，也不承诺整 tick 回滚。周期保存间隔显式配置；首版保存初始快照、结束快照，周期保存可选。若仅保存在内存，进程崩溃后不能承诺恢复。
2. **世界内容。** 保存 W02 的全部 11 项及恢复所需子状态：生命和动作实例、物品/生成器/实体、任务与意图、阶段游标、取消/去重历史、已封口待处理请求、RNG 状态、ID 分配进度、可恢复赛程统计及自然结果。可重建缓存不作第二份真值。
3. **定义和编码。** 快照记录 Schema、代码/规则/地图/档案版本、地图与不可变定义内容哈希；JSON 为首版交换格式，有限 binary64 要能往返恢复，禁止 NaN/无穷。恢复先校验所有引用、模式、哈希和状态，再发布世界；缺定义、版本不兼容或校验失败就拒绝，不自动套新局默认值或降级。
4. **随机性。** 每局显式提供并记录 0 至 2^64−1 的整数种子；首版在固定 CPython 版本下使用 `random.Random`，为世界不同子系统建立有版本、固定名称的独立随机流，并保存每条流完整状态。v1 派生输入为 `b"BedWarsArena.RNG.v1\0" + seed.to_bytes(8, "big") + b"\0" + stream_name.encode("utf-8")`，对其做 SHA-256，将摘要作为大端整数输入该流 `random.Random`。策略和训练随机流单独管理。流名称、派生算法及运行环境写入版本信息；不因此承诺跨平台逐位一致。
5. **标识。** 沿用 W07：本局不透明 ID 由引擎确定性分配，分配进度和已见 ID 历史与提交一起保存；不以现实时间、线程顺序或字典遍历决定。恢复不重发已处理事实。
6. **重放。** 记录初始定义/种子、每轮观测边界、原始请求与校验结果、实际动作、外部替代动作、推进 tick 和终局/截断；记录策略版本和必要运行版本。重放以记录的接收/重试/迟到请求及 Runner 备用决策为输入，已记录的实际动作与处理结果用于核对，不能再作为另一份请求重复投递。快照记录对应日志游标，恢复时不重复提交快照中已经封口或执行过的请求。固定代码、定义、环境与完整记录下，重放应得到相同边界状态和事实序列；可配置定期状态哈希用于定位分歧。重放不依赖策略重新计算，也不暗示跨平台已经验证。
7. **训练恢复。** 训练检查点独立保存模型、优化器、训练进度、学习率调度器及所用 RNG；算法需要经验缓冲区时按其策略保存或明确记录不能精确恢复。若需要连同运行中对局恢复，训练器在一致边界写入关联清单、世界快照、Runner 状态和策略会话状态，校验成功才共同恢复。多文件检查点先写入独立临时目录，完整校验后发布，并原子替换指向已完成检查点的清单；不将尚未写完的文件组作为有效检查点。世界新局不得重置学习状态。

## 4. W12：策略异常与引擎故障

1. **正常无更新**：按 W08 继续原持续动作。某个可解析子请求非法时只拒绝该项；其他独立合法子请求仍按既有规则处理。整包身份/轮次等无效按 W08 拒绝，不自动把该轮每个无效项当成策略故障。
2. **策略异常、超时或必需动作包缺失**：只对受影响玩家生成可追踪的 Runner 备用动作，在下一控制阶段显式取消其移动与交互通道；其他玩家的有效动作照常。取消停止主动移动与未完成交互，不清除既存击退，不撤销已提交效果或独立实体。备用动作有独立请求 ID、正确生命和轮次绑定，并记录原故障、替代及结果；若生命已改变则按 W08 复核，不强加给新生命。
3. **超时能力边界**：墙钟时限显式配置且与 tick 分离。首版进程内只能在回调返回后检测是否超时并丢弃该次结果，不能可靠中断无限循环或原生崩溃；真正强制中止需后续独立进程。不能将软超时宣传成硬隔离。
4. **引擎或规则故障**：受影响的事务/批次不提交，停止推进并报告；此前阶段已提交的内容不声称自动回滚，也不发布不完整 tick 给策略。未知类型、处理器异常、资源上限等按故障处理，不静默跳过、重试或判平局。
5. **恢复**：使用最近的完整边界快照和完整输入日志，在相同定义/版本下显式恢复并重放到所需位置。缺少必需快照或日志时停止并说明，不能假装恢复成功。修复代码后使用不同版本属于迁移或新实验，不能未经验证称精确恢复。

## 5. 观测、奖励与跨局训练的首版衔接

以下是已采用的**首版接口方向**，不是已经实现的 Gymnasium/PettingZoo 兼容性。

### 5.1 观测和智能体生命周期

- 每个活跃玩家只得到独立的自身状态、允许公开的队伍/赛程信息，以及视野内可见的地形、物品和其他玩家；其他玩家背包、行动和隐藏状态不直接暴露。水平视距、B 竖直范围、遮挡材料、视线几何及隐身揭示规则必须在观测档案中显式定义；没有资料时不自动给出一个假定的 Hypixel 数值。
- 外部动作掩码、错误原因、目标选择和 `info` 也按同一权限过滤；完整世界快照、内部日志和诊断不作为参赛观测。可在独立训练档案中明确授权集中式训练信息，但不能悄悄传给执行策略。
- 死亡等待复活期间不请求游戏动作，复活后沿用本局策略会话，不自动重置循环模型隐藏状态。永久淘汰后该玩家在本次训练 episode 中转为**无行动的被动席位**，直到整局结束；只接收授权的自身及公开信息。这样其已发射实体晚到的合法击杀归属仍可进入事件和可配置奖励。
- `action_required=false` 明确表示该席位不需提交动作，不把空动作算作一次策略决策。该玩家的 `terminated` 在整局自然结束时才置真；若整局外部截断则置 `truncated`。训练适配器若用占位 transition，必须标记无有效策略动作，避免把占位值当作实际选择来训练。此选择会增加被动步数据；未来若按个人淘汰终止，需要另定延迟归功语义。

### 5.2 首版奖励与持续学习

- 对战默认采用团队结果奖励：胜队每名成员 `+1`，负队每名成员 `-1`；世界平局时全体成员 `0`，包括 Game End 未处于最高分并列的队伍。单队任务成功时该队每名成员 `+1`、失败时每名成员 `-1`。中途无额外默认塑形奖励；外部截断不虚构胜负或额外终局奖励。破床、击杀等塑形可在单独版本化的奖励档案中显式配置。
- 奖励在训练/接口层由已提交事实与世界结果计算，归属和数值可追踪，不反向改变世界规则。每局结果对包含已淘汰成员的原固定阵容一致计算；实际算法如何折扣或分配奖励由训练器处理。
- 每场对局开始时为每个策略绑定不可变的模型版本；本局结束或截断前不原地改变该版本。训练器可用完成的轨迹持续更新跨局模型，已有对局继续使用旧版本，新对局显式选择新版本；记录每个参赛者对应版本。评估档案冻结模型并不执行训练更新。
- 模型、优化器、算法所需经验与训练计数由训练器管理，不随世界重置或玩家复活重建。会话状态按局创建，复活保留；选择何种算法、批量大小与经验保留策略仍由训练配置决定。

## 6. 仍需落实和核验
