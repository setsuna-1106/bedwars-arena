# 0013：世界引擎职责与 WorldState 顶层结构

日期：2026-10-26；更新：2026-10-27。状态：W01–W09 的已列设计已接受，W09 七组细节见 [0014](0014-w09-world-objects.md)；W10–W12 及训练衔接整组设计随后已采用，完整内容和最新状态见 [0015](0015-world-schedule-replay-failures-and-training.md)。具体数值、对象类型、地图资产和处理器仍待落实，实验行为的 Hypixel 一致性继续核验；完整世界引擎尚未实现。

## 背景与范围

在 PlayerState、TeamState、物理/效果设计及事件排序基础上，明确世界状态的持有者、更新职责、可恢复状态顶层归属、创建/恢复及推进/时间边界。本记录不冻结外部 API 签名、完整输入/输出 Schema 或各子状态内部结构。

已实现的 TeamState 与事件队列基础继续按 [0012](0012-team-core-types-and-ordering.md) 使用；阶段及物理/效果规则继续按 [P/F/V](../physics-effects-confirmation.md) 使用。这里的职责、类型名及数据组织为本平台工程约定，不是 Hypixel 原生内部结构。

## W01：已接受的职责划分

| 部分 | 职责 |
| --- | --- |
| WorldEngine | 独占本局世界状态，按既定阶段推进，调用规则处理器，统一提交状态变更与事实事件。 |
| WorldDefinition | 保存本局固定的规则、地图定义、物理/效果档案、启用机制和玩家/队伍排序；创建后不可变。 |
| WorldState | 保存本局恢复后继续模拟所需的全部可变状态。 |
| 规则处理器 | 分别处理运动、交互、购买、效果、死亡、陷阱等；读取当前状态与定义，返回明确的变更结果，由引擎提交。 |
| 事件调度器 | 管理待办事件、排序和去重；具体玩法判断由处理器完成，不独立推进时间。 |
| 空间查询与缓存 | 提供碰撞、距离、区域和承载查询；缓存从源状态重建，不维护第二份真值。 |
| Runner | 收集同一轮指令，调用引擎统一推进；模型、训练进度与实验调度留在引擎外。 |

- 内部使用引擎独占、受控修改的大型集合；已实现的不可变 TeamState 继续复用。不要求每 tick 深拷贝整个世界。
- 读取世界使用只读查询或独立快照；策略只接收独立的自身观测，不能获得引擎或完整世界引用。
- 处理器不得在自身对象中保留影响未来模拟的隐藏记忆。生成时钟、动作进度、随机源状态等必须进入可恢复状态；处理器可持有代码、不可变定义和可重建缓存。
- 购买、陷阱触发等已有原子性要求继续执行。统一提交不等于已决定整 tick 回滚；故障处理归 W12。

## W02：已接受的顶层结构

这是逻辑结构，尚无完整数据类、Schema 或序列化实现。

```text
WorldState
├── match_id          本局标识
├── definition_ref    固定定义的版本与内容标识
├── tick              已完成结算的 tick；初始为 0
├── players           player_id → PlayerState
├── teams             team_id → TeamState
├── terrain           当前普通方块地形
├── generators        generator_id → GeneratorState
├── containers        container_id → ContainerState
├── entities          entity_id → EntityState
├── execution         可恢复的执行状态
└── result            未结束为空，结束后保存对局结果
```

| 字段 | 已接受的数据边界 |
| --- | --- |
| definition_ref | 关联完整固定的运行定义，包括显式选用的候选与实验参数。恢复须匹配内容，不能只凭可变文件名。具体标识/校验格式待定。 |
| players / teams | 沿用已确认结构。成员关系与队伍淘汰等继续派生，不在根状态重复记账。 |
| terrain | 当前非空气普通方块的三维稀疏字典。地图初始地形用于创建，运行查询以当前地形为准；已加载范围缺键才表示空气。床动态存亡只归 TeamState.bed_state，床几何仍归地图定义。 |
| generators | 资源生成器的动态计时等状态；固定位置、类型与生成规则归定义。内部字段归 W09。 |
| containers | 公共箱、个人箱等容器内容与必要动态状态；随身背包只归 PlayerState。内部字段归 W09。 |
| entities | 掉落物、投射物等具有独立生命周期的对象，以类型区分；玩家单独管理，不能在此重复保存同一玩家。具体类型与载荷归 W09。 |
| execution | 待办事件、调度游标、去重账本、随机源状态、ID 计数器、已接收但未执行的指令，以及 Game End 裁决所需的队伍破床统计；具体布局与执行契约见 W07/W08 和 0015。 |
| result | 未结束时为空；结束后保存已结算的世界结果。胜负、平局、截断和结束后推进归 W10。 |

恢复同一 WorldDefinition 与 WorldState，再输入相同指令，应能继续得到一致结果。首期仍按固定程序版本与运行环境验收，不扩张为未经验证的跨平台逐位一致。

模型参数、优化器、经验缓冲区与完整历史日志由训练/记录模块管理，不随世界状态重置。execution 中恢复必需的去重历史仍属世界状态，不能以日志在外部为由丢弃。

## W03：已接受的创建、重置与恢复原则

| 情况 | 已接受行为 |
| --- | --- |
| 标准新局 | 输入固定定义、随机种子与参赛配置，生成新对局标识，从 tick=0 构造标准初始状态。 |
| 训练场景新局 | 复用同一构造流程，以结构化配置在固定地图上预置已接受范围内的初始状态；同样从 tick=0 开始，预置后仍须满足完整状态约束。 |
| 快照恢复 | 精确恢复时钟、生命序号、待办事件、随机源、ID 计数器等，核对固定定义与版本；不重新播种，也不套用新局默认值。 |
| 世界重置 | 重新创建一局世界；模型、优化器、经验缓冲区与训练计数继续由训练模块管理。 |
| 场景校验 | 检查引用、出生空间、物品容量、效果及已启用机制的处理器/必要参数；缺失定义则创建失败并指出问题，不隐式补零或停用。 |
| 发布初始状态 | 在临时对象中完成构造和校验，全部成功才交给引擎；失败不发布半初始化世界，初始化本身不推进 tick。 |

- 多个世界可以共享不可变定义；可变地形、库存、队列和随机状态各自独立。
- 快照恢复继续原状态；需要修改快照制作训练题时，显式创建新的训练场景，记录来源与修改，不伪装成未经修改的续局。
- 训练预置逻辑范围与默认值已接受，见下节；具体 Schema、关联事件构造细节及 W09 子状态内部字段仍待设计，完整序列化/迁移与快照保存边界归 W11。

### 训练场景：已接受的预置范围与默认值

初始化流程为：选择固定地图 → 创建独立地形状态 → 应用训练预置 → 完整校验 → 发布世界。以下是已接受的逻辑字段范围，不表示加载器或相应机制已经实现。

| 类别 | 允许预置与约束 |
| --- | --- |
| 地图与阵容 | 固定地图 ID、启用队伍和玩家配置；满足地图容量与单局固定阵容约束。 |
| 玩家空间 | 初始位置和朝向；满足碰撞、地图范围及对应物理模式约束。 |
| 玩家物品 | 背包、购买进度、手持物品；统一检查容量和引用关系。 |
| 生命与效果 | 普通生命、吸收生命、已支持的临时效果及剩余时长；遵守效果来源与合并规则，已启用机制所需定义/处理器必须完整。 |
| 队伍 | 床是否存在、升级等级和预置陷阱队列；遵守等级、队列容量等约束。 |
| 资源与容器 | 初始掉落资源、箱内物品、资源生成器初始计时；具体字段随 W09 确定，不将未定义状态当作可直接加载。 |

- 新训练场景也从 tick=0 开始。默认启用玩家存活、life_index=1、本局统计为零、动作双通道为空；标准初始装备/手持等既有默认规则继续适用，显式预置须合法。
- 实例 ID、效果截止时刻与关联事件由构造器统一生成；场景配置不直接改写内部事件队列。
- 从等待复活、飞行中的投射物或进行到一半的动作等复杂中局状态开始时，优先使用快照制作场景。修改快照仍按新训练场景记录来源与修改。
- 预置范围与默认值已接受，不重开讨论；具体输入编码、允许物品/效果目录与 W09 内部字段仍须随后落实。

### 固定地图选择

用户明确地图只需在几个固定地图中选择，不设计地图生成器。新局选择预置地图的 map_id，并绑定对应版本/内容；seed 不生成地形。先提供两张项目自制固定 A 实验地图（两队与四队）已按 0014 采用，具体地图 ID、坐标及文件格式尚未确定；当前没有已实现地图加载器或可运行地图。

训练预置在选定固定地图上构造场景；初始化配置不承担程序化地形生成。对局内按规则放置/拆除方块仍更新当前 terrain，地图固定不意味着局内地形不可变。

WorldState.generators 仍专指铁、金、钻石、绿宝石等资源生成器；不因不设计地图生成器而删除该字段或经济机制。资源生成器的内部结构继续归 W09。

## W04：已接受的推进与时间边界

| 项目 | 已接受决策 |
| --- | --- |
| 最小推进单位 | 引擎每次正常调用推进 1 tick，即 0.05 秒仿真时间，完整执行既定阶段。墙钟耗时不改变仿真时间。 |
| tick 的含义 | 对外发布的 tick=t 表示已完成第 t 个 tick 的结算。初始 tick=0 尚未执行任何推进。 |
| 下一次推进 | 从状态 t 推进时，各阶段统一使用 t+1 作为处理时刻，完成后发布状态 t+1。 |
| 指令生效 | 基于状态 t 收集的指令，在 tick t+1 的控制阶段处理；效果到期/复活等仍遵守既定阶段顺序。 |
| 观测边界 | 仅从初始化完成或完整 tick 结算后的状态构造观测；同轮玩家来自同一状态边界，不暴露阶段中间状态。 |
| 决策频率 | 首期默认每 tick 决策一次；Runner 可以配置每 k tick 决策一次，k 为正整数且记入实验配置。引擎始终逐 tick 执行。 |
| 提前结束 | 每 tick 在结果阶段检查终局；确认结束立即停止，不补满剩余决策间隔。已结束世界再次请求推进，返回明确错误，不改变状态。 |

例如 k=4：基于状态 0 收集一轮指令，只提交一次，在 tick 1 的控制阶段处理，随后逐 tick 执行至状态 4 再收集下一轮。中间 tick 沿用已有持续动作，购买等一次性请求不重复提交；物理/效果/死亡/陷阱仍逐 tick 运行。若 tick 3 的结果阶段确认结束，则停在状态 3。

一次推进的具体调用签名与返回值 Schema 仍待落实，指令校验/迟到原则见 W08，故障处理见 0015 的 W12。完整边界发布不承诺整 tick 自动回滚。运行中的 Phase 仍是 0012，新增 25/32/35/45/55 与完整阶段处理器仍未实现。

## W05：已接受的阶段处理原则

采用固定阶段流水线、逐 tick 更新与定时任务结合的组织方式；保留已接受 P/F/V 的阶段相对顺序及 35/45/55，再按 W09 挂接新增 25 资源生成、32 地面拾取与 0 阶段地面物品到期清理。

| 项目 | 已接受决策 |
| --- | --- |
| 阶段执行 | 每 tick 按既定顺序执行一遍；处理器名单与调用顺序显式固定，不依赖注册到达或字典遍历顺序。 |
| 状态可见性 | 后续阶段读取此前已提交的最新状态，例如 40 购买后的背包变化对 45 交互可见。 |
| 处理器接口 | 读取状态与定义，返回状态变更、待办意图及事实事件，由引擎统一提交。 |
| 连续机制 | 运动、持续交互进度、区域条件、陷阱资格与终局检查逐 tick 执行；没有新指令或事件队列为空时也继续运行。 |
| 定时机制 | 效果到期、复活、周期效果等按明确截止时刻调度；执行时复核生命序号、实例和当前资格，依各事件类型使用相应校验。 |
| 计时真值 | 状态中的截止/下一触发时刻为依据，队列负责调度；刷新/取消后旧任务不能改变新实例。 |
| 缓存更新 | 地形、位置、生命分支或效果变化使相关缓存失效，后续查询须得到当前结果。 |
| 局部重查 | 地形变更等需要补查承载/区域条件时，仅重查受影响对象，不重跑已经结束的整个阶段。 |

例如 45 阶段拆掉承载方块后，重查承载并使相关空间缓存失效：A 在本 tick 的死亡阶段结算，B 按既定规则从下一运动阶段下落。局部重查不能追溯重算已经结束的运动。

同阶段资源竞争、同时拆块与互相致死等按 W06；资源生成、地面拾取及投射物运动/命中阶段挂接已由 0013/0014 采用，完整行为与处理器仍待落实，不能将本节当作完整阶段处理器表。定时任务失效/取消的具体编码与调度边界继续按 W07 落实。

以上仍是设计；当前没有完整世界处理器或物理/效果应用，运行 Phase 也尚未加入 25/32/35/45/55。

## W06：已接受 B 作为冲突结算基础

用户在 A（统一逐笔结算）与 B（竞争操作逐笔、伤害统一结算死亡）中选择 B。本节的 B 是 W06 结算方案，不指物理 A/B 模式。

- 购买、拾取、放置等竞争操作按既定固定顺序逐笔重查与提交，不能重复获得同一份资源或重复占用同一格。既有购买排序/原子性继续保留。
- 60 伤害阶段开始时，依据该阶段开始状态确定攻击资格；伤害按稳定顺序计算，最后在本阶段统一结算死亡。攻击者在本阶段受到致命伤害，不自动撤销其在阶段开始时合格的攻击。
- 因此允许同 tick 互相击杀。例如双方均剩 2 HP，双方近战都满足条件且各造成 3 HP，可在本 tick 同时死亡。
- 护甲、吸收、保护和受击间隔仍按各自战斗规则处理，不能把全部伤害直接相加。具体战斗规则与数值仍待收敛。
- 死亡仍在本 tick 的 60 阶段完成，不推迟到下一 tick；同一生命只结算一次死亡。之后才进行既定的队伍淘汰、陷阱与结果阶段。
- 已发射世界实体继续遵守既有独立生命周期规则；这里不为其新增“来源玩家必须仍存活”的条件。阶段开始的资格冻结只按相应攻击/伤害来源规则执行。

这是一项平台结算选择，不是 Hypixel 精确同 tick 内部时序的核实结论。事件稳定排序基础保留，阶段内伤害/死亡的组织仍需集成实现；没有修改现有调度代码。

### 已接受：同一死亡批次的资源交付

用户修正为：“击杀者本批次也死亡时，资源直接销毁，不会掉落，其他采用”。该修正覆盖此前在击杀者死亡位置掉落的提案；后者未采用。

| 情况 | 已接受处理 |
| --- | --- |
| 有有效击杀归属，击杀者在本批结算后仍存活 | 按既定规则尽量接收四种资源；溢出在击杀者当前位置安全时掉落，否则销毁。 |
| 有有效击杀归属，击杀者本批次也死亡 | 该名死者待转给该击杀者的四种资源直接销毁，不向已结束的生命背包写入，不在双方位置生成掉落，也不改走无击杀者分支；击杀归属和统计保留。 |
| 没有有效击杀者 | 按死者自己的死亡位置判断：安全就地掉落，不安全销毁；不回退最后安全位置。 |

- 先固定本批所有死者在任何资源转移前携带的铁、金、钻石和绿宝石数量，再统一清空并分别计算去向。每份资源只结算一次，不让新接收的资源再次进入本批死亡转移。
- 本批次是否死亡由整个死亡集合决定，不能因遍历先后把尚未处理的死亡者临时当作存活接收者。直接销毁分支不受双方位置是否安全影响。
- 例如甲携带 4 金、乙携带 10 铁并互杀：两份资源均销毁，双方死亡位置都不生成这两份资源的掉落；击杀/死亡正常计数，普通或最终分类沿用既定生命周期规则。
- 这是四种携带资源的结算，不改变非资源物品、箱内容、购买进度或跨死亡统计的既有规则。
- 较早死亡/已淘汰及跨生命投射物击杀的接收政策已在后续确认，见下节；多笔接收的容量顺序仍待细化。

### 已接受：拆建冲突与方块实例

| 情况 | 已接受规则 |
| --- | --- |
| 多人同格放置 | 固定顺序逐笔重查；首个合法请求成功，后续因占用失败，不扣物品。 |
| 多人拆同一方块 | 各自累计进度，不合并；首个合法完成请求移除方块，其余动作因目标消失中断，移除与对应规则结果只结算一次。 |
| 同格拆除与放置 | 对已进入结算的候选按固定顺序处理，每笔读最新地形；不覆盖现存方块，不自动等待/重试，此前已拒绝的请求不自动恢复。 |
| 拆后原位重建 | 引擎内部区分方块实例。相同位置/材质的新放置方块仍为新实例，旧拆块进度/完成事件不能作用于它。 |
| 多人同时完成破床 | 在既定 50 阶段按固定顺序处理，首个合法请求取得破床归属；床只摧毁并记录一次。 |

例如甲拆掉旧方块，乙随后合法放回同材质方块，丙针对旧方块的拆除进度失效，需要重新下令。是否进入候选及各次校验仍遵守动作契约，不能让此前被拒绝的放置请求在拆除后自动恢复。

普通方块实例标识及拆块动作绑定关系是恢复所需状态，具体编码、初始实例分配与新 ID 生成随类型/快照设计落实。外部策略不因此获得任意指定内部实例的权限。床仍是既有的逻辑床对象，动态存亡只归 TeamState.bed_state，不在普通地形增加第二份床状态。

### 已接受：较早死亡与跨生命资源接收

前提是对局仍在进行、世界实体本身仍有效，并已按对应规则确认有效击杀归属。击杀统计归来源玩家；资源能否接收看该玩家在本批死亡结算后的生命状态。

| 击杀者状态 | 已接受处理 |
| --- | --- |
| 等待复活 | 保留有效击杀归属与统计；对应四种资源直接销毁，不掉落。 |
| 已永久淘汰 | 保留有效击杀归属与统计；对应四种资源直接销毁，不掉落。 |
| 已复活且本批结算后仍存活 | 资源交给当前新生命背包，容量与溢出沿用既定规则。 |

这是一项已接受的平台规则，不作为 Hypixel 线上跨生命结算的实测证据。具体来源字段、事件编码、实体类型与行为处理器仍待实现。

### 已接受：死亡批次提交

先生成完整结算计划，校验通过后一次提交。本节确定 W06 的引擎提交契约，不补充尚未确认的战斗公式、归因窗口、掉落几何或具体规则数值。

| 步骤 | 已接受行为 |
| --- | --- |
| 确定死亡集合 | 汇总本阶段伤害与虚空等死亡请求，按 (match_id, player_id, life_index) 去重，同一生命只结算一次。 |
| 固定结算依据 | 保存死亡位置、转移前资源、有效击杀归属和当前床状态；决定复活/淘汰及普通/最终统计。 |
| 构造最终结果 | 计算生命转换、动作/效果清理、购买进度/冷却处理、资源去向、统计及复活任务，暂不修改正式状态。 |
| 统一校验 | 检查引用、生命序号、背包容量及资源账目。每种资源满足：本批转出量 = 接收量 + 掉落量 + 销毁量。 |
| 一次提交 | 受影响玩家、掉落物、相关调度任务及 ID 分配进度一起提交，随后统一输出事实事件。 |
| 后续阶段 | 成功后才执行 70 队伍淘汰、80 陷阱及 90 结果检查。 |

- 每名玩家只构造一份最终更新；同一玩家兼具击杀者/死者角色时合并全部击杀/死亡计数，不让基于旧副本的更新互相覆盖。
- 本批构造或校验失败，不提交本批变化并停止本次推进。此前阶段如何恢复及整 tick 故障策略继续归 W12，不将批次提交解释为已采用整 tick 回滚。
- 复活/淘汰、life_index、临时效果清理、装备进度与按组冷却继续按已接受生命周期规则处理，不在此重复建立默认值；等待中丢床不取消已经授予的复活资格。
- 当前 EventQueue 只有排序/去重/恢复基础，完整引擎须把相关调度变化纳入批次提交。现有队列的弹出不等于完整世界业务成功，事务处理尚未实现。

## W07：已接受的三类消息语义

| 类别 | 已接受含义 | 示例 |
| --- | --- | --- |
| ScheduledTask：待办任务 | 在指定 tick/阶段尝试执行，届时仍须校验有效性。 | 复活任务、效果到期、周期效果触发。 |
| Intent：阶段内意图 | core 产生的候选操作，在目标阶段复核并结算；产生意图不代表成功。 | 破床意图、伤害意图。 |
| FactEvent：事实事件 | 状态成功提交后形成的不可变记录。 | 玩家死亡、床被摧毁、资源转移。 |

- 定时队列管理待办任务。需要跨阶段保留的意图归 execution；未来 tick 的工作由规则显式创建任务。
- 取出任务不代表业务成功；只有成功提交的世界变化才产生对应事实事件。
- 核心统计随状态提交更新，事实事件供记录、回放与过滤后的智能体反馈使用，不通过外部消费者重复更新玩家核心统计。
- 策略动作请求归 W08；Intent 由 core 生成，策略不能直接声明已通过规则检查的意图。

例：45 阶段拆床进度完成后产生破床意图，50 阶段复核并成功提交床状态后输出床已摧毁的事实事件，60 阶段死亡结算读取更新后的床状态。意图本身不提前生成成功事实。

三类消息的字段组织、数量限制和版本兼容原则也已接受，见下文六组收尾方向；完整字段表、具体阈值与迁移实现继续落实。现有 ScheduledEvent/EventQueue、运行 Phase 与快照版本没有修改，不能把新分类记为已实现类型或已有事务能力。

### 已接受：调度边界与任务处理

| 项目 | 已接受规则 |
| --- | --- |
| 完整 tick 边界 | 在已结算状态 t 创建任务，目标只能为 t+1 或更晚。 |
| 推进过程中 | 当前 tick 新任务只能投递到尚未开始的后续阶段；未来 tick 可指定任一合法阶段。 |
| 当前阶段联动 | 作为当前结算计划的一部分处理，不重新向当前阶段投递任务。 |
| 非法投递 | 拒绝过去 tick、当前阶段或已结束阶段的投递，不自动顺延；阶段进度由引擎判断，空阶段也算已走过。 |
| 完成判定 | 取出任务后先校验并构造结果；成功提交时一起提交状态、队列与游标变化。 |
| 正常失效 | 旧生命、已替换实例或已取消任务等正常跳过，记录内部原因，不生成对应的玩法成功事实。 |
| 执行故障 | 未知任务类型、处理器异常等为引擎故障；不提交本批、不继续推进、不自动重试，此前阶段恢复归 W12。 |
| 后续任务 | 周期机制按自身规则显式安排下一次，失效的旧任务不能自行续期。 |

例：当前执行 45 阶段时，可以安排本 tick 55 阶段或下一 tick 0 阶段任务，不能安排本 tick 20/45 阶段任务；45 内饮药生效仍属于当前事务。既有稳定排序与同 ID 去重规则继续沿用。

本节不只依赖队列上一次 pop 的游标判断阶段进度；即便队列为空，已运行阶段也不能回填。现有队列未实现该世界阶段校验或完整事务，后续须按版本显式集成。

### 已接受：逻辑取消与分类型校验

- 动作取消、效果替换或对象结束时使对应任务失效；旧任务到期出队后正常跳过。
- 显式取消标记与对应状态变化一起提交，进入可恢复的 execution 状态。
- 可以清理已确定失效的队列项，但保持有效任务顺序与去重历史。
- 取消不撤销已提交结果，也不自动删除已发射世界实体。

| 任务类别 | 已接受的执行前校验 |
| --- | --- |
| 当前生命动作/效果任务 | 对局、玩家、life_index、存活分支，以及对应实例仍有效。 |
| 复活任务 | 玩家仍等待复活、生命序号及 respawn_at 匹配；保留已获准资格，不按当前床状态再次撤销。 |
| 独立世界实体任务 | 实体仍存在并满足自身规则；来源玩家死亡不自动使其失效。 |

涉及到期/周期触发时还须核对当前 expires_at、next_trigger_at 等时刻，避免刷新后的旧定时任务误触发。语义按任务类别定义，不把 AliveState 校验套用于所有任务。

这是 core 内部任务管理；策略通过 W08 动作请求表达取消，不获得直接操作任务队列或移除已购陷阱的权限。既有陷阱只追加购买/正常触发消费、已提交结果不回滚等约束保留。

逻辑取消/校验尚未实现；消息标识、去重保留与因果追踪的已接受规则见下节。

### 已接受：消息标识、去重保留与因果追踪

| 项目 | 已接受规则 |
| --- | --- |
| 内部标识 | 引擎按确定性处理顺序分配内部 ID，本局内唯一；分配进度随对应提交保存并进入快照，跨局以 match_id 区分。 |
| 新实例与重试 | 新任务、意图或事实分配新 ID；同一消息重试保留原 ID。取消或失效的 ID 不能重新激活；这不授权引擎自动重试故障。 |
| 去重保留 | 已见 ID 的去重记录保留到本局结束，随快照恢复。清理无效队列项不删除去重历史；同 ID 同内容忽略，同 ID 不同内容拒绝。 |
| 直接因果 | caused_by 保存直接上游的类别与 ID，可引用内部消息或动作请求；根消息为 null。它用于追踪，执行资格仍依据当前状态校验。 |
| 提交分组 | 同一次提交产生的事实共用 commit_id，各事实仍有独立消息 ID。 |

例：任务 T1 产生意图 I1，I1 成功结算产生事实 F1/F2；I1 的 caused_by 指向 T1，F1/F2 的 caused_by 指向 I1，两个事实共用提交标识 C1。这里的简写仅作示意，不要求 ID 前缀可解析。

本节确认标识与追踪原则，不修改现有队列 schema 1，也未实现新的 ID 分配器、消息类型或提交分组。外部请求 ID 的约束继续归 W08；完整快照、分配器编码与跨版本恢复归 W11 配合落实。

## W08：已接受的请求身份、重复提交与生命绑定

| 项目 | 已接受规则 |
| --- | --- |
| 请求与运行状态 | 外部请求只表达动作及参数；ActionState 的执行身份、进度和开始时刻由引擎维护，策略不能直接填写或改写运行状态。 |
| 请求身份 | 使用 (match_id, player_id, request_id) 识别请求；对局和玩家身份由 Runner/适配器绑定，策略不能靠修改消息身份控制其他玩家。 |
| 重复提交 | 同 ID、同内容返回已有的可见处理状态，不重复执行；同 ID、不同内容拒绝。再次购买相同商品属于新请求，使用新 ID。 |
| 生命绑定 | 玩家动作携带 life_index，接收和执行时校验当前生命；旧生命指令不能在复活后执行。 |

请求身份与运行中的 action_id 分开；新的请求 ID 不自动意味着必须替换或重启动作，相同持续动作仍按 0009 保持原实例/进度。一次性请求重试不再次扣费、发货或产生第二次执行。返回已有处理状态仍受玩家观测/信息边界约束，不直接暴露内部诊断或隐藏信息。

同请求的重复查询不产生新的动作，也不能绕过生命绑定将旧请求重新投入新生命。已发射世界实体继续按自身生命周期处理；来源生命结束不撤销此前已提交的发射结果。

本节未冻结完整 ActionRequest 字段表、request_id 分配方式或参数规范化/内容比较编码。校验分层、接收/执行时序、决策轮绑定/迟到过期、同轮多请求/整包处理、瞬时操作/购买数量顺序、显式取消与请求状态/反馈均已接受，见下文；四种请求状态语义已定，完整反馈 Schema 与原因码表仍待落实。现有 ScheduledEvent/EventQueue 的内部去重不等于外部请求接收器；外部接收与执行 API 尚未实现。

| 接收校验 | core 检查对局、玩家、请求身份和生命绑定；通过后记录为待处理。接收本身不推进 tick。 |
| 接收与成功 | 已接收只表示进入处理流程，不保证玩法操作成功，也不提前扣费、扣物或预留资源。 |
| 开始与结算 | 开始动作前检查启动条件，实际结算时按机制重查当前资源、目标、距离、冷却等条件；只检查该机制实际要求的条件。 |
| 失败与原动作 | 新请求启动条件不合法时保留原动作；合法开始后再失效，则按既定中断规则结束，已丢弃的旧进度不恢复。 |

例：两名队友购买同一目标等级的升级，请求均可被接收；购买阶段按固定顺序逐笔复核，只有成功的一笔扣费。接收记录不锁定升级资格或资源，已接收请求不能绕过 W06 的竞争结算。

本节不改变 W04 的下一 tick 控制时刻、各机制既定的扣物/扣费点或 W06 的统一提交方式。接口层不依据完整隐藏世界代替 core 做玩法判断；拒绝与失败反馈仍遵守信息边界。已接收的恢复必需数据归 execution，完整字段/状态枚举仍待落实；决策轮绑定/迟到过期、同轮多请求/整包处理与显式取消见下文。接收器、启动/结算校验和完整世界处理器均未实现。

### 已接受：决策轮绑定、输入封口与迟到/过期

| 项目 | 已接受规则 |
| --- | --- |
| 决策轮绑定 | Runner 为本轮绑定 decision_round_id 和观测边界 observed_tick=t；请求归属该轮，在 t+1 控制阶段处理。决策轮标识与 tick 分开，不要求数值相同。 |
| 输入封口 | Runner 收集完成后封闭本轮输入，再推进世界。封口后不能新增或替换本轮请求。 |
| 迟到与过期 | 新到请求若属于已关闭决策轮，或观测边界不匹配，则拒绝，不自动移到下一轮。已接收并封入批次的请求按原定时刻处理。 |
| 未来请求 | 首版不接受策略预先提交未来轮次的请求；未来定时机制仍由 core 内部任务管理。 |
| 重复请求 | 已记录请求的同内容重试仍返回已有可见状态，即使原轮已关闭，也不重新执行。 |

配置 k>1 时，本轮请求仍只在第一个 tick 提交一次，中间逐 tick 模拟；已有持续动作继续按自身规则运行，且终局立即停止。迟到按决策轮与仿真边界判断，策略计算耗时不推进世界，不因现实时间过去而自动推进 tick。

已封入批次的请求进入 t+1 后仍按原定时刻处理，不因此时处理时钟已进入下一 tick 而被误判为新到过期请求；开始/执行资格仍按当前生命和玩法条件复核。已记录请求的重复查询不重新入队，也不能通过修改轮次、观测时刻或生命绑定规避同 ID 异内容拒绝规则。

这是首版同步接入的请求时序，不限制 core 自身创建未来 ScheduledTask。精确恢复时仍需保留已接收请求和必要执行进度，不重新套用新到请求判断；快照边界及异常/软超时/必需输入缺失的备用处理随后已按 0015 采用，不将它们自动视为正常保持。批次封口、迟到校验与完整 Runner 尚未实现。

### 已接受：同轮多请求与整包处理

| 项目 | 已接受规则 |
| --- | --- |
| 提交单位 | 每位玩家每轮提交一个动作包，各子请求保留独立 request_id 和处理结果。 |
| 通道上限 | movement、interaction 每轮各最多一个更新。先去重；不同请求 ID 同时更新同一通道时，拒绝该通道本轮所有更新，保留原动作，不按到达先后覆盖。 |
| 包级错误 | 外层结构或共同的对局、玩家、轮次、生命绑定不合法，整包拒绝。 |
| 子请求错误 | 子请求可以独立解析时，单项错误只拒绝该项，其他独立合法请求继续处理。 |
| 执行顺序 | 各请求按固定阶段和处理器顺序执行，不以通信到达顺序或 JSON 字段顺序决定；整个动作包不保证全部成功或全部失败。 |

例：移动请求合法、攻击请求非法时，移动仍可执行，攻击失败不撤销移动。不同 ID 的两条移动更新即使动作内容相同，仍属于同通道多更新冲突；同 ID 同内容的重试先去重，不制造第二次更新。保留原动作不免除其自身的持续合法性检查。

动作包的部分成功语义不取消单笔购买、物品使用或死亡批次等既定的原子提交要求，也不允许把未完成交互自动排队或重试。包级/子请求拒绝与引擎故障仍分开处理；策略异常、软超时和必需输入缺失的替代行为已按 0015 采用。瞬时操作/购买数量顺序及显式取消见下文；完整包 Schema 继续细化。动作包接收、冲突检查与分项反馈尚未实现。

### 已接受：瞬时操作与购买的数量和顺序

| 项目 | 已接受规则 |
| --- | --- |
| 瞬时操作数量 | 每玩家每轮最多一次转向、一次手持切换，两者分别计数。 |
| 购买数量 | 首版每玩家每轮最多一笔购买，商品、团队升级、陷阱合计计数；购买不占持续动作通道。一笔商品交易按商店报价单位发货，可以包含多个物品。 |
| 超限处理 | 先去重；超过某组上限时，拒绝该组本轮全部请求，其他组继续处理。 |
| 控制阶段顺序 | 20 阶段按转向 → 手持切换 → 移动通道更新 → 交互通道更新处理；后续动作使用更新后的朝向和手持。 |
| 购买结算 | 购买仍在 40 阶段，读取此前已提交的最新位置、背包和队伍状态，逐笔校验并提交。 |

上述数量为首版平台输入约定，不是 Hypixel 现服操作速率或单次购买限制的核验结果。上限按决策轮而非每个模拟 tick 计数；k>1 时不在中间 tick 重交、补发或自动重复购买。

本轮购买的新物品尚不能用于本轮 20 阶段的手持切换；购买成功后不自动重试切换，需要下一轮下令。例：20 阶段请求切换至当前背包没有的新剑则切换失败，40 阶段购买成功只更新背包，不自动改手持。若原先已有对应物品，则按实际库存检查切换，不因本轮另有购买而一律拒绝。

各组失败仍按整包部分成功语义处理；无效转向/切换不把未发生的朝向/手持变化当成事实，后续请求按实际已提交状态校验。合法切换引起的交互中断不因后续新交互请求失败而撤销，也不恢复已丢弃进度。购买规则与消费点、动作朝向/冷却等既定规则保留。具体控制处理器、分组计数与购买 API 尚未实现；显式取消及请求状态/反馈见下文。

### 已接受：显式取消

| 项目 | 已接受规则 |
| --- | --- |
| 表达方式 | 正常省略某通道表示保持；取消必须提交明确的 cancel 请求，并指定通道。 |
| 取消目标 | 取消处理时该通道的当前动作；通道已经为空时，返回无变化结果。 |
| 时序与数量 | 在 20 阶段对应通道更新的位置处理，计入该通道每轮一次更新。取消与新动作同时更新同一通道，按冲突规则全部拒绝。 |
| 动作清理 | 清空对应动作和未完成进度，使关联旧任务失效；另一通道继续，取消后不自动恢复。 |
| 保留状态 | 不重置冷却、不清除已生效效果。取消移动只停止主动移动，击退继续按物理规则运行。 |
| 取消范围 | 首版仅取消自身持续动作通道；已完成交易、已放置方块和已发射实体按原规则保留，陷阱队列不开放主动移除。 |

例：取消尚未完成的饮药会丢弃进度，不扣药水；已经饮用成功的药效继续存在。转向/手持切换仍先于通道更新；若此前的合法切换已使交互中断，随后对已空通道的取消返回无变化，不重复终止旧动作。

取消请求沿用对局/玩家/轮次/life_index、去重与封口规则，不能绕过旧生命隔离或修改已封闭输入。取消对应动作的状态清理与必要任务失效按既定统一提交/逻辑取消规则完成，旧任务不能复活动作；同内容重试不再次终止。此处不授予直接操作执行队列、取消世界实体或撤销一次性购买的接口。

已采用的是取消语义与 20 阶段挂接；请求状态与反馈也已采用，见下节。完整字段、公开原因码表与具体处理器尚未实现。普通省略通道的保持不等于算法异常/软超时/必需输入缺失的替代策略，后者按 0015 的 W12 处理。

### 已接受：请求状态与对外反馈

| 项目 | 已接受规则 |
| --- | --- |
| 请求状态 | rejected：接收阶段拒绝；accepted：已接收、待处理；applied：请求已成功应用；failed：接收后未能应用。 |
| 持续动作结果 | applied 表示动作控制已生效；动作之后完成或中断，另行记录并关联 action_id，不改写原请求结果。 |
| 无变化操作 | 保持相同动作、取消空通道等返回 applied，结果注明无变化，不生成虚假的动作终止事实。 |
| 反馈关联 | 可识别的请求返回请求 ID、决策轮、实际处理 tick、状态和稳定原因码；涉及持续动作时关联动作 ID。整包错误单独反馈。 |

例：饮药请求先成为 applied，表示开始饮用；后来被取消，动作结局记录为中断，原请求仍保持 applied。取消请求自身也有独立请求身份及处理结果，不通过改写原始请求结果表示后来发生的中断。

同内容请求重试返回已有可见状态，不重新执行，不重复产生动作完成/终止事实。反馈中的实际处理时刻不因 k>1 的下一轮集中交付而改写成较晚交付 tick。可即时返回的接收回执不开放阶段中间世界状态，完整执行结果仍按 W04 的共同完整边界发布；查询、状态、原因码与关联标识均须遵守同一信息边界。

## W09：已接受的资源生成器结构

本节的 generators 指铁、金、钻石、绿宝石等资源的生成器，不是地图生成器。固定地图选择与局内拆建约束保持不变。

| 项目 | 已接受设计 |
| --- | --- |
| 建模单位 | 每种资源产出流独立一条记录；同一基地的铁、金可以共用位置，但分别计时。 |
| generator_id | 引用固定定义中的产出流标识，资源类型、位置和所属队伍从定义查询。 |

| schedule_id | 当前计时计划的实例 ID；重排计划时换新，使旧任务失效，快照恢复时保留。 |

GeneratorState 的基础三字段为 generator_id、next_spawn_at、schedule_id，归 WorldState.generators。标识与时间继续使用平台不透明字符串 ID、整数 tick/明确允许的 null；不通过 ID 前缀推导资源或队伍，不用独立倒计时替代 next_spawn_at。

周期、产量与积累上限由版本化规则决定，执行时与当前规则状态配合查询。依据 BW-ECON-03，规则资料需继续区分模式、地图和升级等条件；本节不冻结任何生成速度、数量、上限或现服同刻行为。缺少所需规则参数不能通过设置 null 或补默认数值使生成机制静默失效。

生成任务仍按 W07 复核当前计划/截止时刻，过期计划不能产生资源；地面资源实际数量只有实体状态一份真值，积累查询或缓存不建立第二份可变余额。三字段只确定逻辑结构，具体 Schema、生成处理器与地面实体类型尚未实现。

### 已接受的实验方案：满额计时与生成余量（Hypixel 待核验）

用户采用持续周期检查、不累计欠产量的方案。本节是明确的平台实验规则；BW-ECON-03/04 的官方/社区证据状态保持不变，尚未核实其与 Hypixel 现服完整行为一致。周期、产量和积累上限本身不因采用该算法而获得默认值。

| 情况 | 已接受处理 |
| --- | --- |
| 到期时已满额 | 本次不生成，下次尝试仍为本次到期 tick 加周期；不将生成器标为停用。 |
| 有空间但不足一次产量 | 只生成剩余容量允许的数量，保证不超过上限。 |
| 拾取后腾出空间 | 等下一个既定生成时刻，不立即补发，也不重跑已结束的生成阶段。 |
| 曾因满额跳过生成 | 跳过的产量不累计，之后不会集中补发。 |

例：假设某实验档案周期为 20 tick，100 时满额跳过，105 时资源被取走，下一次仍在 120 尝试生成。这里的 20 tick 只用于示例，不是任何资源的 Hypixel 周期参数。

按下节已采用的实验统计口径取得当前积累数量 C、上限 L 与单次产量 A，实际生成数量为 min(A, max(0, L-C))；当前积累已经达到或超过上限时本次生成零。该公式只约束本次新增生成数量，不授权删除已有地面资源。

满额时当前有效计时计划仍继续安排下一次检查；失效的旧任务仍按 W07 跳过且不续期。零产出不能记录为资源已经生成，也不记作待偿还产量。正常生成/检查后的截止时刻和关联调度变化沿用引擎统一提交原则；具体处理器与调度集成尚未实现。

积累统计、首次生成/周期变化/启停实验方案及生成/拾取阶段也已采用，见下文；拾取细则、地面物品、容器与独立实体继续确认，不能从本节补出其默认行为。

### 已接受的实验方案：积累上限统计口径（Hypixel 待核验）

本节与满额计时方案一起作为明确的平台实验规则采用，Hypixel 一致性继续待核验；不把玩家丢物、区域边界或重叠统计的模拟选择升级为官方规则。

| 项目 | 已接受规则 |
| --- | --- |
| 统计区域 | 地图显式配置三维半开矩形区域，以掉落物的参考位置是否在区内判断，不默认范围大小。 |
| 统计数量 | 累加区域内仍有效的同类地面物品数量，计数单位为物品数量。 |
| 资源来源 | 生成器产出、人工丢物、死亡掉落及其他生成器移入的同类资源，均计入。 |

同类统计区域重叠时，各自独立统计；同一实体可以影响多个覆盖它的区域，数量仍只在实体中保存一份。例：玩家手动丢入的铁会占用铁的积累额度，金的额度不受影响；放入背包或容器后不再作为地面积累计入。

半开区域各轴使用 [min, max)；具体坐标与尺寸由地图显式声明，掉落物参考位置的字段/编码随地面实体结构落实。资格以当前实体状态与参考位置判断，不用生成来源替代空间查询；来源仍可用于追踪。统计结果或索引缓存须随相关实体变化失效/更新，不建立另一份可变资源余额。

积累查询只供 core 按规则执行，公开观测与反馈继续遵守信息边界，不因内部区域统计开放隐藏资源信息。具体数量上限、地图区域数据、实体几何/类型及查询处理器尚未实现。首次生成/升级启停实验方案及生成/拾取阶段见下文，下一步地面物品与拾取细则，再细化容器和独立实体。

| 情况 | 已接受规则 |
| --- | --- |
| 新局首次生成 | 规则显式配置首次等待，至少 1 tick；初始化只安排任务，首次时刻为创建时刻加首次等待。 |

| 明确停用 | 将 next_spawn_at 设为 null，替换计划标识使旧任务失效；已有地面资源保留。 |

例：原定 100 生成，90 时周期由 20 改为 10，仍在 100 尝试生成，之后为 110、120。本次等待保留，提速从后续周期体现；即使本次因满额产出零，也按有效的新规则周期安排后续检查。示例数值仅说明实验算法，不是任何资源的 Hypixel 参数。

### 已接受：DroppedItemState 基础结构与数量提交

DroppedItemState 归 WorldState.entities，保存地面物品的唯一动态状态，不在生成器、队伍或玩家记录中复制地面数量。

| 字段 | 已接受含义 |
| --- | --- |
| entity_id | 本局唯一的不透明实体 ID。 |
| item_key、quantity | 每个实体保存一种物品及其正整数数量，物品键复用背包目录。 |
| spatial | 保存参考位置和模拟所需速度；参考位置取物品碰撞体中心，用于积累区域统计。 |
| created_at | 创建时的整数 tick。 |
| pickup_ready_at | 最早允许拾取的绝对 tick；到时仍需检查玩家、空间和容量等资格。 |
| expires_at | 到期消失的绝对 tick；只有规则明确永久存在时才为 null，未知寿命不能当作永久。 |
| source | 记录生成器、玩家丢弃、死亡或训练预置等来源，用于追踪，不自动授予拾取权限。 |

基础结构共有八个字段（item_key 与 quantity 分开）；位置/速度继续按既定有限 binary64 空间量处理，标识/时间沿用不透明字符串和整数 tick。source 的具体类型与来源标识编码、spatial 内部结构和物品目录映射仍待落实，不据此复制完整玩家或队伍状态。

部分拾取时，背包增加与地面数量减少一起提交；数量归零则移除实体，不保留仍可拾取的零数量记录。来源玩家死亡不自动删除该实体，实体按自己的有效性和时限处理。物品数量变化与实体移除须使相关积累/空间缓存失效，不能把可重建缓存作为第二份数量真值。

本节只采用结构与数量结算原则，不冻结实际出生位置/速度、碰撞尺寸、寿命、拾取延迟、堆叠上限、合并拆分或生成器分享规则；普通掉落物竞争顺序见下文，这些数值不能自动补零、无限或其他默认值。沿用 0 到期清理、32 拾取及晚于 32 新掉落物最早下一 tick 拾取的既定挂接，具体资格仍由 core 判断。

| 收到分享的队友 | 获得分享不自动再次触发；之后若轮到该队友且地面仍有资源，可按资格正常拾取。 |
| 无合格队友 | 触发者没有符合条件的队友时，按普通拾取处理，不产生额外资源。 |

合格队友按已采用的队伍、存活与分享范围判断；容量决定实际接收数量，不用满背包重新定义队伍/空间资格。每笔读取此前最新提交，先构造并校验，再提交实际地面扣减、参与者所得、额外产量及必要分享消耗记录；同一已取走的份额不再次参与普通或分享结算，地面未取走的余量则仍可依序处理。

例：10 个铁，红队 A 先取 4、合格红队友得 4，地面剩 6；之后符合条件的蓝队 B 取 6、合格蓝队友得 6，地面归零。两笔只消费不同地面份额，额外发放分别为 4 和 6。分享范围实验规则见下节；已消费份额如何跨实体合并拆分记录、具体类型和处理器仍待落实。

### 已接受的实验规则：生成器分享范围

2026-10-27，用户采用以下平台实验几何；[历史玩家指南](https://hypixel.net/threads/guide-bedwars-etiquette-when-playing-with-teammates-3s-4s-strategies-and-defenses.5282787/) 提到资源周围约 2 方块的分享区域，属于社区候选而非现服实测。以下玩家参考点、竖直判定与遮挡处理是平台建模选择，不据此声称与 Hypixel 服务端算法一致。

| 项目 | 已接受规则 |
| --- | --- |
| 水平区域 | 以资源碰撞体中心的水平位置为圆心；队友水平矩形中心落在半径 R 的圆内即可，边界包含。 |
| 实验半径 | 该实验档案显式配置 R=2 方块；可调整并记录规则版本，不自动用于其他规则档案。 |
| 正式 B 竖直范围 | 资源中心高度须落在队友脚底至头顶的身体高度区间，向上和向下各扩张 V 后的闭区间内。V 必须显式配置，未知值不默认零或无限。 |
| 前期 A | 在既定单一行走层实验中只检查水平范围，不额外进行竖直检查。 |
| 遮挡 | 不额外检查视线，满足条件时允许隔墙分享。 |
| 检查时机 | 32 阶段触发拾取时检查当前位置；队友仍须满足已采用的同队、存活等资格。 |

形式化地，水平条件为 `(x_player - x_item)^2 + (z_player - z_item)^2 <= R^2`；B 模式还需 `y_foot - V <= y_item <= y_foot + H + V`。这里 `(x_player,z_player)` 为玩家水平中心，`y_foot` 为脚底，`H` 为身体高度，`(x_item,y_item,z_item)` 为地面物品碰撞体中心。触发者仍按普通拾取条件检查；参与分享的队友不必满足普通拾取距离。

A 中资源位于 `(0,0)`、R=2 时，队友位于 `(2,0)` 为边界内，位于 `(1.5,1.5)` 则在圆外。相关坐标与规则参数继续遵守已有有限 binary64 及版本化容差约定；R=2 是已采用的实验配置，不是已经核实的现服参数。分享 B 的 V、普通拾取距离/延迟及物品寿命仍须配置；处理器尚未实现。

## W10：已接受的标准对战自然终局

2026-10-27，用户采用以下对局结果规则。适用范围为开局至少有两支参赛队伍、启用标准对战胜负规则的场景；单队训练任务及外部训练时限分别按后续已采用规则处理。本平台的同时全灭平局与精确结算顺序不声明为 Hypixel 现服已核验行为。

每个 tick 在 90 结果阶段，根据已经完成 60 死亡、70 队伍淘汰等阶段后的最新状态，统计仍可参赛队伍：队伍至少一名成员处于 `AliveState` 或 `RespawningState` 时仍可参赛；全员 `EliminatedState` 才淘汰。床的存续不单独决定队伍是否仍可参赛。

| 仍可参赛队伍数 | 已接受结果 |
| --- | --- |
| 两队及以上 | 通常继续；若游戏自身 Game End 到期，则按 [0015](0015-world-schedule-replay-failures-and-training.md) 比较。 |
| 恰好一队 | 该队获胜。 |
| 零队 | 平局，无胜方。 |

例：两队均无床，最后成员在同一死亡批次互相最终击杀并同时淘汰，则结果为平局；若另一队有成员已获准复活且正在等待，该队仍可参赛，不把全队等待误判为淘汰。若它成为唯一仍可参赛的队伍，则获胜，不额外等待该次复活完成。

自然结果进入世界结果状态后按 W04 停止，不补满 Runner 的 k tick；已结束世界再次推进报错且不修改状态。最终结果和观测按完整 tick 边界发布，正常死亡、个人暂时等待复活不自动结束整局。此节只定义开局至少两队的标准对战自然结果；训练外部时限截断和单队训练任务结束分别见后文，游戏自身 Game End、奖励和单智能体终止语义已按 [0015](0015-world-schedule-replay-failures-and-training.md) 采用；结果类型与处理器尚未实现。

### 已接受：训练外部时限截断

2026-10-27，用户采用以下训练边界：游戏自然终局与训练设置的外部时限截断分别反馈。这里借鉴 [Gymnasium 的终止/截断区分](https://gymnasium.farama.org/tutorials/gymnasium_basics/handling_time_limits/)，不因此决定引入该框架或完成其 API 适配。

| 情况 | 已接受反馈与处理 |
| --- | --- |
| 游戏自然决出胜负或平局 | 返回 `terminated = true`，记录实际胜负，世界按 W04 自然结束。 |
| 达到训练时限但游戏未结束 | 返回 `truncated = true`，不生成胜负；本次训练局停止，最后世界状态仍可用于快照。 |
| 自然终局与训练时限在同一 tick 发生 | 优先自然结果并记录实际胜负，两个标志均为 true；见 0015。 |
| 时限配置和检查 | Runner 显式配置仿真 tick 数，在每个完整 tick 后检查；即使 k>1 也不越过时限补满决策间隔。 |
| 最终反馈 | 返回经过权限过滤的最终观测，避免把训练截断伪装为对局胜负。 |
| 持续学习 | 本次训练局结束时不自动清空模型、优化器或经验缓冲区。 |

例：当前完整边界为 tick 96，决策间隔 k=4，训练上限为 tick 98；Runner 只推进 97 和 98，在 98 停止，不推进 99、100。若游戏恰好在 98 自然终局，优先返回自然结果，同时保留达到时限的记录；若没有自然结果，则为训练截断。

以上时限是 Runner 的外部训练边界，不将游戏本身的 `Game End` 直接当作外部截断。后续按 [0015](0015-world-schedule-replay-failures-and-training.md) 采用：同刻自然终局和到达时限时两个标志均为 true，以自然结果为主要结果；单智能体反馈、时限基准/恢复和策略超时/异常处置也已确定方向。完整结果 Schema、训练、Runner 与世界 API 尚未实现。
